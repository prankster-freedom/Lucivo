# knowledge-intake（ノウハウの取り込み）

ユーザーが、ノウハウを分割して送ってくる場面で使う。分割して送るのは、一度に多くを送ると量がかさむため。
取り込みは、「すべて共有しました」の連絡で終わりとする。途中で要約や反映を始めない。

対象: $ARGUMENTS

## 1. 受け取り（共有の途中）

- 受け取った内容は、要約せずに保管する。ユーザーが「トークン節約のため、ここに出力しなくてよい」と指示しているので、受け取るたびに内容を書き出さない。
- 応答は「受け取りました。保管します。」のように短くする。
- 会話が長くなると、前の画像の細部が失われることがある。受け取ったその場で、本文と見本の内容を作業ファイル（`work/intake_<対象>.md`。git の管理外）に書き写しておく。会話には出さない。反映が終わったら、ユーザーに確かめてから消す。
- 画像は、本文の抜き出しと、読み取った内容を後でまとめるために、保管しておく。スキャン画像そのものはスキルに入れない（データ量が多くなるため）。
- 本文だけでなく、**見本の写真（作例、Before/After）も取り込みの対象**とする。言語化が難しくても、何をして、なぜそう見えるかを文章にする。後回しにしない。
- 途中で、ユーザーから止める指示や方針の変更があれば、それに従う。

## 2. 終了の判定

- 「すべて共有しました」の連絡で、取り込みの終了とみなす。
- 連絡がまだなら、反映は始めない。「まだ保管しています」とだけ返す。

## 3. 反映の準備（終了の連絡のあと）

1. 保管した内容を、分野ごとに分ける（例: 手順、道具、考え方、注意点）。章の構成（前提となる章、手順、道具、例）と、章どうしのつながり（例: 前提の章の判断が、後の手順の基準になる）を読み取る。要約ではなく、理由と例まで含めて理解する。
2. 既存のスキルと照らし合わせ、どこに反映するかを決める。
   - 既存のスキルの範囲に入るなら、そのスキルに追記する。
   - どのスキルにも入らず、独立して使う手順や知識なら、新しいスキルを作る。
   - 原則（どの作業にも共通する考え方）は `AGENTS.md`、リポジトリ固有の規則は `AGENTS.repo.md` に書く。スキルに書かない。
3. 反映の案を、ユーザーに示して承認を得る（`AGENTS.md` 1.2）。承認のあとで書き込む。

## 4. 画像のまとめ方

スキャン画像は、そのままスキルに入れない。まずテキストで書けるかを判断し、画像は必要な場合だけ残す。
リポジトリのサイズとスキル読み込み時のトークン消費を抑えるため、画像を増やさない。

1. **テキストで書く（既定）**: 本文の要点、手順、一覧、比較は、Markdown の見出し・箇条書き・表で書く。図の内容も、文章と表で伝わるならテキストにする。配置や対比を見せたいときは、まずコードブロックの**テキストのポンチ絵**（□・■・○ などの記号で描く図）で表せないかを考える。
2. **ポンチ絵（SVG）を残す条件**: 位置関係、流れ、図と地のような、テキストでは伝わりにくい図だけ。SVG は `assets/` に置く。
   - トークンの節約より、伝わることを優先する。テキストで伝わらないもの（ページの中の配置の関係、実際の色、ぼかしなどの見え方の比較、作例の Before/After）は、テキストで済ませず、SVG で図にする。伝わらないテキストは、節約にならない。
   - SVG には `<title>` と `<desc>` で、図が示す内容を書く。SVG を開けない環境でも、意図が読み取れるようにする。
   - SVG は、テキストで書いた内容を図にするためのものとする。SVG だけで内容が伝わるように、文字も SVG に入れる。
   - 作ったら、SVG を開いて、文字がはみ出していないかを確かめる。はみ出していたら、文を短くして直す。
3. **PNG は原則として作らない**: SVG で足りる。どうしても必要なとき（SVG を表示できない環境向けなど）だけ、ユーザーに確認してから作る。
   - 作る場合は、SVG を Chromium（Playwright）で描画して保存する。
4. **出典**: 章とページ番号を書く。書名は、ユーザーが示した場合だけ書く。

スキルの本文が画像を参照するときは、必要な場面でだけ開く。`assets/` のファイルを、毎回読み込まない。

## 5. 作業の進め方（git）

- 反映は、`main` から新しいブランチを切って行う（`AGENTS.md` と `branch-strategy` に従う）。
- 共有ファイル（`.claude/`・`AGENTS.md` など）の変更は、共有ファイル以外を含まない独立したコミットにする（`AGENTS.md` 4 章）。
- コミットと push、PR の作成は、ユーザーの指示があってから行う。コミットの名義はユーザー本人にし、AI の署名は入れない（`AGENTS.md` 1.13）。

## 6. 書き方の注意

- 書籍などの内容（実証）と、自分の応用・解釈（推論）を区別して書く（`AGENTS.md` 1.1）。応用の節には「推論」と明記する。
- 例は、元の資料の例をそのまま使う。架空の例を作らない。

## 7. 完了の報告

- 反映したスキル、新しく作ったスキル、ポンチ絵の場所を一覧にする。
- 内容が未確認の部分（読めなかった章など）は、未確認と明記する。
- 追記が必要な箇所があれば、次の取り込みの候補として挙げる。
