# cr（変更要求）

既存のソフトウェアへの変更要求（CR: Change Request）を登録し、影響する工程から対応を進め、対応済みになるまで追跡する。新しい機能をはじめから作る場合は、swe1 から進める。

CR の進め方に固有の改善（分類・票の項目・手順の見直しなど）は、本スキルを更新して反映する（`AGENTS.md` 1.5）。

対象: $ARGUMENTS

## CR として扱うもの

| 扱うもの                                                       | 扱わないもの（扱い先） |
| :------------------------------------------------------------- | :--------------------- |
| 利用者・ユーザーからの不具合の指摘、使い勝手へのフィードバック、仕様の変更依頼 | 進行中の増分の中で見つかった、その増分の仕様どおりに直す誤り（その工程の中で直す） |
| test・dtp（校正）で見つかり、その場では直さない所見            | 誤字・リンク切れなど、仕様に影響しないドキュメントの修正（doc スキル） |
| 要求・設計の前提の変更（外部仕様やライブラリの制約の変化など） |                        |

## Work Product (WP: 成果物)

1. **GitHub Issue**: GitHub 上に起票される Issue（`#<番号>`）。Type（`Bug`, `Feature`, `Task`）およびラベル（`bug`, `enhancement`, `UI` 等）を設定し、CR の一次情報源として追跡する。ひな形は [template.md](template.md) の「GitHub Issue」。
2. **CR 票（任意・リポジトリの方針による）**: `<プロジェクト>/doc/6.change_request/<サービス>/CR-<SVC>-<nnn>_<件名>.md`。リポジトリ側でファイルベースの CR 管理を併用する場合に作成する。ひな形は [template.md](template.md) の「CR 票」。
3. **CR 一覧（任意・リポジトリの方針による）**: `<プロジェクト>/doc/6.change_request/README.md`。ID・件名・分類・状態・優先度・Issue 番号・対応する PR を載せる。ひな形は [template.md](template.md) の「CR 一覧」。

格納先と ID 体系は doc スキルの「ソフトウェアプロジェクトのドキュメント」「ID 体系」に従う。リポジトリ固有の格納先は `AGENTS.repo.md` を優先する。

## 分類と GitHub Issue の Type・ラベル

指摘を、現在の仕様（FR / DD）に照らして分類し、GitHub Issue に設定する Type とラベルを決定する。分類によって、直す対象と戻る工程が決まる。

| 分類   | 判定 | 推奨 Type (`--type`)    | 推奨ラベル (`--label`)                          | 直す対象・戻る工程 |
| :----- | :--- | :---------------------- | :---------------------------------------------- | :----------------- |
| 不具合 | 仕様どおりに動いていない | `Bug` | `bug`（画面崩れ等は `UI` も付与）             | 実装（swe3）。仕様の書き漏れが原因なら swe1・swe2 から |
| 仕様の変更 | 仕様どおりに動いているが、仕様が利用者の目的に合わない | `Feature` または `Task` | `enhancement`（見た目・操作なら `UI` も付与） | 要求（swe1）。見た目の変更は dtp から |
| 追加   | 現在の仕様にない要求 | `Feature` | `enhancement`（見た目を伴う場合は `UI` も付与） | 要求（swe1）。見た目を伴う場合は dtp から |

- 上記に加え、内容に応じて `documentation`（ドキュメント）、`performance improvement`（性能改善）、`CI` / `GitHub Workflow`（自動化・ワークフロー）等のラベルを適切に組み合わせる。
- 仕様どおりの動きへの指摘を、不具合として実装だけで直さない。要求仕様書が古いまま残り、後の変更で元に戻される。

## 状態

| 状態     | 意味                                                                                   |
| :------- | :------------------------------------------------------------------------------------- |
| 登録     | 内容・分類・影響範囲を整理し、対応するかどうかの判断を待っている（Issue が open）      |
| 承認     | 対応する方針と範囲が決まった                                                           |
| 対応済み | 影響する工程の成果物を更新し、テスト（必要なら校正）に合格した（PR で Issue が close） |
| 保留     | 対応する時期を決めていない（理由と、再開する条件を Issue に書く）                      |
| 却下     | 対応しない（理由を Issue に書いて close）                                              |

対応済みの CR は、対応の変更を含む PR が main に反映されたことをもって完了とする。完了のために CR 票を更新し直す必要はない。

## 手順

1. **既存の Issue・CR と仕様の確認**: GitHub Issue（`gh issue list`）および CR 一覧から、重複・関連する Issue や CR を探す。要求仕様書・設計書・テスト仕様書・デザイン仕様書から、指摘に関係する現在の仕様（FR / DD / TC / DTP）を確かめる。
2. **変更要求の分析**:
   - **分類と Type・ラベル**: 上記の「分類と GitHub Issue の Type・ラベル」に従って分類し、設定する Type とラベルを決める。根拠となる FR / DD の ID を示す。
   - **原因**: 再現手順と確認した結果から原因を特定する。推測で書かない。特定できない場合は、その旨と確かめるために必要なことを書く（`AGENTS.md` 1.1）。
   - **影響範囲**: 影響する FR / DD / TC / DTP の ID と、戻る最初の工程を示す。
   - **対応案**: 案が複数ある場合は比較し、採る案、採らなかった案とその理由、副作用（他の機能・表示・操作への影響）を示す。
   - **規模の見積もり**: 作業の規模を見積もる（`AGENTS.md` 1.11）。マイルストーン等で複数案件を計画する場合は、難易度（低/中/高）と向くモデル区分（軽量/標準/上位）、ユーザーの在席・不在スケジュールに応じたフェーズ分け（例: 不在中に低難易度案件を一括実装・一括E2Eテスト、復帰後に高難易度案件を実施）を整理して提案する。その際、提示された時間枠を絶対的な上限（タイムボックス）とし、安全マージン（2〜3割）を引いた枠内で確実に終わる規模に絞り込む。遅延の予兆がある場合や予定期限を迎えた場合は、沈黙せず期限到来前に状況・理由・見通しを報告することを徹底する（`AGENTS.md` 1.11）。
   - 1 件の依頼に複数の指摘が含まれる場合は、対応するかどうかを個別に判断できる単位に分け、それぞれを 1 件の Issue にする。対応は 1 つの PR にまとめてよい。
3. **【承認】CR の登録と対応方針の確認**: Issue のタイトル、Type、ラベル、本文案（概要・再現手順/背景・原因・影響範囲・対応案・戻る工程・見積もり）を示し、CR ごとに対応するかどうかの承認を得る。
   - 承認を得たら、GitHub CLI（`gh issue create`）で起票する。
   - 記号（`\`、`$`、バッククォート等）の破損を防ぐため、本文は一時ファイル（`work/` 配下等）を作成し、`--body-file` で渡して起票する（`AGENTS.repo.md` 3 章）。
   - 起票完了後、発行された Issue 番号（`#<番号>`）と URL を報告する。
   - ファイル管理を併用するリポジトリでは、CR 票および CR 一覧にも Issue 番号を紐づけて登録・更新する。
4. **対応**: 戻る工程から順に、影響する工程だけを各スキルの手順で進める（`dtp → swe1 → swe2 → swe3 → test → dtp → commit` のうち影響する工程）。
   - コミットメッセージや PR の説明文に、関連 Issue 番号（`fixes #<番号>` または `#<番号>`）を明記する。
   - 各工程の成果物に CR / Issue の ID を記載する（要求・設計を変えた項目、TC の対応する ID の列）。
   - 仕様・設計の背景・根拠と採らなかった案は、Issue だけでなく、要求仕様書・設計書の本文にも残す。本文にないと後の変更で同じ検討が抜け落ちる（`AGENTS.md` 1.9）。
   - 対応の途中で影響範囲が広がった場合は、Issue にコメントを残し、前の工程に戻ることを提案する（`AGENTS.md` 1.3）。
5. **対応結果の記録**: 変更した成果物の ID、合格した TC の ID、対応するブランチと PR を記録し、状態を「対応済み」にする。CR 票と CR 一覧を管理している場合は、対応する変更と同じ PR で更新する。
6. **【承認】対応結果の確認**: CR ごとの対応結果と、残った課題（新しい Issue として登録するもの、保留にするもの）を報告し、承認を得たら完了とする。
