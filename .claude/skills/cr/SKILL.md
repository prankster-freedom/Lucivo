# cr（変更要求）

既存のソフトウェアへの変更要求（CR: Change Request）を登録し、影響する工程から対応を進め、対応済みになるまで追跡する。新しい機能をはじめから作る場合は、swe1 から進める。

CR の進め方に固有の改善（分類・票の項目・手順の見直しなど）は、本スキルを更新して反映する（`AGENTS.md` 1.5）。

対象: $ARGUMENTS

## CR として扱うもの

| 扱うもの                                                       | 扱わないもの（扱い先） |
| :------------------------------------------------------------- | :--------------------- |
| 利用者・ユーザーからの不具合の指摘、使い勝手へのフィードバック、仕様の変更依頼 | 進行中の増分の中で見つかった、その増分の仕様どおりに直す誤り（その工程の中で直す） |
| test・dtp（校正）で見つかり、その場では直さない所見            | 誤字・リンク切れなど、仕様に影響しないドキュメントの修正（doc スキル） |
| 要求・設計の前提の変更（外部仕様やライブラリの制約の変化など） |                        |

## Work Product (WP: 成果物)

1. **CR 票**: `<プロジェクト>/doc/6.change_request/<サービス>/CR-<SVC>-<nnn>_<件名>.md`。ひな形は [template.md](template.md) の「CR 票」
2. **CR 一覧**: `<プロジェクト>/doc/6.change_request/README.md`。ID・件名・分類・状態・優先度・影響する要求・対応する PR を載せる。ひな形は [template.md](template.md) の「CR 一覧」

格納先と ID 体系は doc スキルの「ソフトウェアプロジェクトのドキュメント」「ID 体系」に従う。リポジトリ固有の格納先は `AGENTS.repo.md` を優先する。

## 分類

指摘を、現在の仕様（FR / DD）に照らして分類する。分類によって、直す対象と戻る工程が決まる。

| 分類       | 判定                     | 直す対象・戻る工程                                     |
| :--------- | :----------------------- | :----------------------------------------------------- |
| 不具合     | 仕様どおりに動いていない | 実装（swe3）。仕様の書き漏れが原因なら swe1・swe2 から |
| 仕様の変更 | 仕様どおりに動いているが、仕様が利用者の目的に合わない | 要求（swe1）。見た目の変更は dtp から |
| 追加       | 現在の仕様にない要求     | 要求（swe1）。見た目を伴う場合は dtp から              |

仕様どおりの動きへの指摘を、不具合として実装だけで直さない。要求仕様書が古いまま残り、後の変更で元に戻される。

## 状態

| 状態     | 意味                                                             |
| :------- | :--------------------------------------------------------------- |
| 登録     | 内容・分類・影響範囲を整理し、対応するかどうかの判断を待っている |
| 承認     | 対応する方針と範囲が決まった                                     |
| 対応済み | 影響する工程の成果物を更新し、テスト（必要なら校正）に合格した   |
| 保留     | 対応する時期を決めていない（理由と、再開する条件を書く）         |
| 却下     | 対応しない（理由を書く）                                         |

対応済みの CR は、対応の変更を含む PR が main に反映されたことをもって完了とする。完了のために CR 票を更新し直す必要はない。

## 手順

1. **既存の CR と仕様の確認**: CR 一覧から、重複・関連する CR を探す。要求仕様書・設計書・テスト仕様書・デザイン仕様書から、指摘に関係する現在の仕様（FR / DD / TC / DTP）を確かめる。
2. **変更要求の分析**:
   - **分類**: 上記の「分類」に従って分類し、根拠となる FR / DD の ID を示す
   - **原因**: 再現手順と確認した結果から原因を特定する。推測で書かない。特定できない場合は、その旨と確かめるために必要なことを書く（`AGENTS.md` 1.1）
   - **影響範囲**: 影響する FR / DD / TC / DTP の ID と、戻る最初の工程を示す
   - **対応案**: 案が複数ある場合は比較し、採る案、採らなかった案とその理由、副作用（他の機能・表示・操作への影響）を示す
   - **規模の見積もり**: 作業の規模を見積もる（`AGENTS.md` 1.11）
   - 1 件の依頼に複数の指摘が含まれる場合は、対応するかどうかを個別に判断できる単位に分け、それぞれを 1 件の CR にする。対応は 1 つの PR にまとめてよい
3. **【承認】CR の登録と対応方針の確認**: CR 票の案（分類・原因・影響範囲・対応案・戻る工程・見積もり）を示し、CR ごとに対応するかどうかの承認を得る。承認の結果に応じて、CR 票と CR 一覧を状態「承認」「保留」「却下」で登録する。
4. **対応**: 戻る工程から順に、影響する工程だけを各スキルの手順で進める（`dtp → swe1 → swe2 → swe3 → test → dtp → commit` のうち影響する工程）。
   - 各工程の成果物に CR の ID を記載する（要求・設計を変えた項目、TC の対応する ID の列）
   - 仕様・設計の背景・根拠と採らなかった案は、CR 票だけでなく、要求仕様書・設計書の本文にも残す。CR 票は対応済みになった後には読まれにくく、本文にないと後の変更で同じ検討が抜け落ちる（`AGENTS.md` 1.9）
   - 対応の途中で影響範囲が広がった場合は、CR 票の影響範囲を更新し、前の工程に戻ることを提案する（`AGENTS.md` 1.3）
5. **対応結果の記録**: 変更した成果物の ID、合格した TC の ID、対応するブランチと PR を CR 票に記録し、状態を「対応済み」にする。CR 票と CR 一覧の更新は、対応する変更と同じ PR に含める。
6. **【承認】対応結果の確認**: CR ごとの対応結果と、残った課題（新しい CR として登録するもの、保留にするもの）を報告し、承認を得たら完了とする。
