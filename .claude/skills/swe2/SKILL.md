# swe2（SWE.2: ソフトウェアアーキテクチャ設計とブランチ作成）

アーキテクチャ設計とブランチ作成、計画の更新を行う。ソフトウェア開発の工程は swe1 → swe2 → swe3 → test → commit の順に進める。

対象: $ARGUMENTS

## Work Product (WP: 成果物)

1. **ADS (Architecture Design Specification)**: `<プロジェクト>/doc/ADS.md`（または `doc/2.ARCHITECTURE.md`）
   - システム全体のアーキテクチャ、構成要素（コンポーネント分割・配置）、利用技術の選定
   - コンポーネント間のインターフェースおよびデータフロー
   - 設計判断の背景・根拠、採らなかった案とその理由
   - 主要な依存関係の版の方針（「依存関係の版の管理」）
   - 各要素と要求仕様 ID（FR / NFR）のトレーサビリティ
2. **SwcRS (Software Component Requirement Specification)**: `<プロジェクト>/doc/SwcRS/<コンポーネント名>.md`
   - 詳細な要求仕様を定義したほうが良い SWC（ソフトウェアコンポーネント）についてのみ作成する

## 手順

1. **既存の設計書の確認**: ワークスペースにアーキテクチャ設計書が既に存在するかを確認する（格納先は doc スキルの「ソフトウェアプロジェクトのドキュメント」）。
   - 存在する場合: 既存の内容を十分に理解し、それをベースに作業を進める
   - 存在しない場合: 新規に作成する
2. **アーキテクチャ設計案の作成**: arc42 などの確立されたテンプレートを参考に、アーキテクチャ設計（ADS）を構造化して記述する。また、複雑なコンポーネント等で必要と判断される場合は SwcRS を作成する。設計の各要素には、対応する要求仕様の ID（`FR-xxx` / `NFR-xxx`）を記載する。依存関係を選定・更新するときは、「依存関係の版の管理」に従う。
3. **【承認】設計案とブランチ戦略の確認**: アーキテクチャと利用技術の案、ブランチ戦略（ブランチ名は commit スキルの「ブランチ規則」に従う）をユーザーと協議し、承認を得る。前工程の計画に変更が出た場合は、あわせて提示する。
4. **反映とブランチ作成**: 承認された内容を設計書に反映し、承認されたブランチを作成する。
   - 設計判断の背景・根拠（なぜその構成・技術にしたか、前提とした制約、採らなかった案とその理由など）は、後の設計変更でのデグレを防ぐため、該当する設計要素の近くに記載する
   - 議論の経緯（いつ・誰が・どのようなやり取りで決めたか）は設計書に書かず、コミットメッセージの本文に残す（`AGENTS.md` 1.9）
5. **【承認】最終版の確認**: 最終版のドキュメントをユーザーに報告し、明示的に承認を得たら完了とする。

## 依存関係の版の管理

依存関係（プロジェクトが利用する外部のライブラリ、フレームワーク、ランタイムなど）は、緊急の修正をパッチの適用だけで取り込める状態を保つ。

- **リリースポリシーの確認**: 選定するときと更新を計画するときに、提供元が公開しているリリースポリシーを確認する。
  - リリースの区分（latest、stable、LTS など）と、本番利用に推奨される区分。区分の名前と意味は提供元ごとに異なるため、名前だけで判断しない（例: Node.js は Current と LTS を分け、本番では Active LTS か Maintenance LTS を使うよう案内している）
  - リリースの周期、保守の期間、修正が提供される版の範囲、非推奨の扱い
- **使う版の選び方**:
  - ポリシーが公開されている場合: 本番利用に推奨される区分のうち、修正が提供される版を使う。メジャー版のリリース予定や保守の終了に合わせて、更新の時期と確認の作業を前もって計画に入れる。ポリシーに明記がない事項（同じ区分に複数のメジャー版がある場合にどこまで使えるかなど）は、公開されていない場合の方針に従う。
  - ポリシーが公開されていない場合: 最新の版か、その 1 つ前の版を使う。最新の版は修正が早いが、新しい不具合を含むことがある。1 つ前の版は利用実績があるが、修正が提供されないことがある。どちらのリスクが低いかは一概に決まらないため、変更履歴や不具合の報告を確認して選び、根拠を ADS に記載する。
- **版の遅れの上限**: どちらの場合も、基準の版（本番利用に推奨される区分の最新の版。区分がなければ最新の版）から、マイナー版で 2 つ以上遅れた状態を基本的に避ける（例: 基準が 5.7 なら 5.6 までに保つ）。
  - 背景: 修正が提供される版の範囲は限られる。例えば [GitLab のメンテナンスポリシー](https://docs.gitlab.com/ja-jp/policy/maintenance/) では、バグ修正は現在の安定版だけに行い、セキュリティ修正は現在の安定版と過去 2 回の月次リリースに行う。範囲を外れた版で緊急の修正が必要になると、マイナー版やメジャー版の更新まで同時に行うことになり、影響の確認に時間がかかる。
- **設計書への記録**: 主要な依存関係について、使う区分と版の方針、参照したリリースポリシーのリンク、分かっている保守の終了時期を ADS に記載する。ポリシーが公開されていない場合は、その旨を記載する。
- **例外**: 互換性の問題などで上限を超える場合は、理由、セキュリティ上の影響、解消の見通しを ADS に記載し、ユーザーの承認を得る。
