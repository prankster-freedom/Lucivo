# GitHub の設定と手順

[ブランチ戦略の考え方](SKILL.md)を GitHub で実現する方法を定める。

## main への反映

GitHub の PR のマージ操作は、マージコミット、Squash、Rebase の 3 種類で、fast-forward がない。Rebase and merge は親と内容が同じでもコミッターの日時を更新するので、コミットの SHA が必ず変わる。このため、PR の承認を条件に GitHub Actions が fast-forward する。

| PR の作成者        | 承認の操作                   | 状況                                        |
| :----------------- | :--------------------------- | :------------------------------------------ |
| リポジトリの所有者 | PR に `/self-approve` と書く | [self-approve.yml](self-approve.yml) で動く |
| 他の開発者         | GitHub の Approve            | 未整備。開発者を追加するときに作る          |

- 自分の PR は GitHub の Approve ができないため、`/self-approve` は **リポジトリ関係者が 1 人の場合の PR 承認の代替手段** として用いる（複数人で開発する場合は通常の GitHub Approve を使う）
- `/self-approve` を利用するかどうか、および通常の開発 PR と正式リリース PR（`release/*`）のどちらで必須とするかは、各リポジトリの `AGENTS.repo.md` に明記する
- Canary 運用を行うリポジトリでは、通常の開発 PR は必須チェック（`lint`・テスト等）が通れば `/self-approve` を経ずに `main` へマージしてよい（`main` を Canary プレビューの基準とする）。正式リリース時は `release/vX.Y.Z` ブランチから版番号定義と `README.md` のみを更新した PR を作成し、必ず PR 承認（1 人運用の場合は `AGENTS.repo.md` の定めに従い `/self-approve` 等）を経て `main` へ反映する
- `/self-approve` は、所有者が所有者自身の PR に書いたときだけ、`test` の成功またはスキップと、PR が最新の main の上にあることを確かめて反映する
- 導入するときは、[self-approve.yml](self-approve.yml) を `.github/workflows/` に置き、必須チェックのジョブ名を合わせる。`issue_comment` は既定のブランチにある定義で動くので、導入の PR だけは Rebase and merge で反映する
- Rebase and merge のボタンはコミットを作り直すため、導入後は使わない。リポジトリに 1 つはマージ方法を残す必要があるので、設定では無効にできない
- PR が最新の main の上にないときは、先にリベースする
- シェルからコメントするときは、Git Bash がコメントをパスに変換しないよう、`MSYS_NO_PATHCONV=1` を付ける

### 他の開発者を追加するとき

- フォークからの PR に限る場合は、書き込み権限が所有者だけなので、承認なしの反映は起きない
- 書き込み権限を与える場合は、次を決めてから追加する
  - ルールセットの必須の承認と CODEOWNERS
  - Approve を条件に反映するワークフロー。`pull_request_review` は PR 側の定義で動くため、書き込み権限を持たせない。`workflow_run` で既定のブランチの定義に引き継ぎ、API で承認の内容を確かめ直す
  - 手元からの main への push が拒否されること。PR 必須のルールは、オープンな PR のコミットの push を止めないことがある

## CI

- 必須チェックの対象のワークフローを `paths-ignore` でスキップしない。ワークフロー全体がスキップされると、必須チェックが待機のままになり、PR をマージできなくなる
- 変更されたファイルを調べるジョブを先に動かし、テストのジョブを `if` でスキップする。`if` でスキップされたジョブは必須チェックを満たす
- テストのジョブの条件は、判定の結果が明確に「スキップ」のときだけ飛ばす形にする（例: `!cancelled() && needs.changes.outputs.e2e != 'false'`）。判定のジョブが失敗したときに必須チェックを素通りさせないため
- スキップの対象は、テストに関係しないと確かなパスだけを列挙する。`.github/workflows/` は対象にしない。配布物の中の Markdown など、`**/*.md` の一括の除外で巻き込むものに注意する
- PR の追加 push において、直前 push からの増分差分がテストに関係しないパス（ドキュメントや版番号のみの更新）だけであり、かつ直前コミットでテストが成功している場合はテストをスキップしてよい。直前のテスト結果が確認できない場合や失敗していた場合は必ずテストを実行する
- テストは `pull_request` で実行し、main への `push` では実行しない。必須チェックとブランチの最新化の要求により、main には検証済みのコミットだけが入るため
- リリースビルド（ビルド番号注入）・タグ作成・GitHub Release 公開・公開サイト同期は、モバイル環境等からのリリースにも対応できるよう、`main` への反映や `workflow_run` をトリガーに CI で自動化する構成を標準とする

## リポジトリの設定の方針

### 全般

- Issues はオン、Wiki はオフ、Discussions はオフ。文書はリポジトリの中で管理する

### マージ

- 許可するマージ方法は Rebase and merge だけとする
- PR の Update branch ボタンはオン、auto-merge はオフ
- ブランチの自動削除はオン。ただし fast-forward の反映では働かないので、self-approve.yml が削除する

### main の保護

既定のブランチを対象にルールセットを作り、例外（bypass）を設けない。

- ブランチの削除と force push を禁止する
- 線形履歴を必須にする
- PR を必須にする。必須の承認数は、開発者が 1 人の間は 0 とする（1 以上にすると、自分の PR を反映できない）
- テストのジョブを必須ステータスチェックにし、ブランチの最新化も必須にする

### GitHub Actions

- 許可するアクションは GitHub 製のみとする
- `GITHUB_TOKEN` の既定の権限は読み取りのみとし、PR の承認は許可しない。書き込みが必要なジョブだけ `permissions` で宣言する
- 書き込み権限で動くワークフローでは、PR のコードを実行しない

### セキュリティ

- Secret scanning、Push protection、Dependabot alerts はオン
- Dependabot security updates は、自動の PR で依存関係の整合が崩れないことを確かめてからオンにする
- 公開リポジトリでは、非公開の脆弱性報告をオンにし、`SECURITY.md` で案内する

### 適用の順序

1. Actions の許可範囲を変え、CI の成功を確認する
2. そのあとで、テストのジョブを必須ステータスチェックにする。先に有効にすると、PR をマージできなくなる

### 公開配布の前に行うこと

- Topics と Homepage を設定する
- 版のタグ（例: `v*`）の削除と更新を禁止する
- Immutable releases は、版が 1.0.0 に達してから適用する
