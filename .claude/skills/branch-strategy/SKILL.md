# branch-strategy（ブランチ戦略）

ブランチ戦略の考え方と、それを Git ホスティングサービスの設定で実現する方法を定める。リポジトリの設定の変更は、ユーザーの指示があるときだけ行い、適用後は設定値を読み直して結果を報告する。リポジトリごとの例外は `AGENTS.repo.md` に書く。

対象: $ARGUMENTS

## ブランチ運用の基本的な考え

- **main への変更は PR と必要な承認・検証を経る**: 個々の開発者の手元から main へ直接 push しない。承認や必須チェックを経ずに反映できる経路を作らない。Canary 運用を行う場合、通常の開発 PR は必須チェックの通過で main へ反映し、正式リリース PR（`release/*` ブランチ）では必ず PR 承認を経て main へ反映する。PR 承認の方法（複数人での Approve、またはリポジトリ関係者が 1 人の場合の代替手段である `/self-approve` を利用するかどうか）と Canary 運用の採否は、各リポジトリの `AGENTS.repo.md` に定める
- **公開版と Canary 版の分離**: 本番公開・配布物は最新の正式リリースタグを基準とし、Canary プレビューは `main` を基準にデプロイする
- **履歴を一直線に保つ**: マージコミットを作らない
- **検証したコミットをそのまま反映する**: PR で検証したコミットを、作り直さずに main へ反映する
- **必要なテストを迂回させない**: 必須チェックを外したり、結果が残らない形でスキップしたりしない。判定できないときはテストを実行する
- **不要なテストを回さない**: テストに関係しない変更ではテストを省く。同じ内容を検証する実行を重ねない
