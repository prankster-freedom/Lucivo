状態・採否の理由・再利用の条件は [ラフ案台帳](../README.md) を正とする。

┌──────────────────────────────────────────────────┐

│ ┌──────────┬────────────┬───────────┐            │

## RGH-107 表紙のメタ情報行

```text
        文書の題名
   山田 太郎  ·  2026-11-06  ·  14 STAGES  ·  6 FIGURES
```

- ストック。`author` は文字列のことも入れ子（`name`・`role`）のこともあり、`date` も形式が文書ごとに違うため、確実に読み取れない。章数は目次と重なる。

## RGH-108 発表の表紙に目次を出す

```text

│          文書の題名             │
│  01 …   04 …   07 …  10 …      │ ← 押しても送りにならない
└───────────────────────────────┘
```

- ボツ。発表はクリックで次のシーンへ送るため、目次は押せる道案内にならない。題名の主役を弱める。

## RGH-111 比較型（Before / After の左右対置）

```text
┌──────────────────────────────────────────────────┐
│ STAGE 04  従来との比較                             │
│ ┌─ BEFORE ───────────┐  →  ┌─ AFTER ────────────┐ │
│ │ （彩度を落とす）    │     │ （アクセント色）    │ │
│ │ ・手作業で 3 日     │     │ ・自動で 10 分      │ │
│ └─────────────────────┘     └─────────────────────┘ │
└──────────────────────────────────────────────────┘
```

- 狙い: 講演で多い「従来と新しい方法の比較」を、左右の対置と彩度の差で一目で見せる。左は沈め、右を主役にする（`DTP-001` の主役は 1 つ）。
- 判定の候補: 章に `###` の小見出しが 2 つだけあり、その語が対になっている（`Before` / `After`、`従来` / `新方式` など）。
- ストックの理由: 対になる語の一覧を決めないと誤判定が出る。2 つの小見出しの章は要点カード型（`RGH-002`）でも表せる。比較の章が意図どおりに見えないという要望が出たら再検討する。

## RGH-112 タイムライン型（日付つきの箇条書き → 横の年表）

```text
┌──────────────────────────────────────────────────┐
│ STAGE 07  ロードマップ                             │
│                                                  │
│  2026 Q1      2026 Q3      2027 Q1      2027 Q3   │
│ ──●───────────●───────────◉───────────○────────▶ │
│  α 版        β 版        正式版       拡張       │
│                          ↑ 現在（光る点）          │
└──────────────────────────────────────────────────┘
```

- 狙い: ロードマップや沿革を、手順型（`RGH-003`）とは違う「時間の軸」として見せる。現在の位置を光の点にし、過去は塗り、未来は輪郭だけにする。
- 判定の候補: 箇条書きのすべての項目が、日付・年・四半期（`2026`、`2026 Q1`、`2026-04` など）で始まる。日付の書式はセルの文字だけで判定できる（`RGH-101` と同じ考え方）。
- ストックの理由: 「現在」をどう決めるか（閲覧した日か、文書に書いた日か）が未確定。項目が 7 個を超えるときの折り返しも未検討。

## RGH-115 定義リスト型（用語と説明の 2 段組）

```text
┌──────────────────────────────────────────────────┐
│ STAGE 03  用語                                     │
│                                                  │
│  Slab        │ 1 章を載せる面。角丸と影で独立する   │
│  ─────────── │                                    │
│  Scene       │ 発表で 1 度に映す単位                │
│  ─────────── │                                    │
│  ↑ 等幅・太字   ↑ 本文                             │
└──────────────────────────────────────────────────┘
```

- 狙い: 技術発表で多い用語の説明を、辞書のような 2 段組にする。用語を等幅で揃えると、ブランドの「丸みのある等幅」（1.2.5）の論理性が出る。
- 判定の候補: 箇条書きのすべての項目が `**用語**: 説明` または `用語 — 説明` の形。
- 採用した形（`DTP-VTPL-045`）: 区切りの揺れは、ダッシュ区切りの `**用語** — 説明` だけを用語集とすることで解消した。コロン区切りは要点カード型の書き方のため対象外とする（`RGH-909`）。長い用語は用語の列の中で折り返す。

## RGH-909 定義リスト型をコロン区切りの 7 項目以上でも判定する

```text
- **用語**: 説明   ← 要点カード型（2〜6 個）と同じ書き方
  …（7 個以上）    → 用語集にする案
```

- ボツ。`**題**: 説明` は要点カード型（`RGH-002`）の書き方で、7 個以上は「カードにせず標準のリストに戻す」規則（`DTP-VTPL-001`）がある。項目の数だけで用語集に切り替えると、同じ書き方が個数によってカード・用語集・リストの 3 通りに変わり、書き手が結果を予測できない。区切りをダッシュ（`—`）にした項目だけを用語集にする（`RGH-115`）。

## RGH-910 コールアウトの色を Visualモードの 4 色に置き換える

```text
NOTE → --vs-c3   TIP → --vs-c4   WARNING → --vs-c2   CAUTION → --vs-c1
```

- ボツ。スタイルによって `--vs-c1` がコーラル（警告に見える）にもダスティローズにもなり、CAUTION と NOTE の区別が崩れる。注意書きの色は意味を運ぶため、スタイルに依らない意味の色（青・緑・紫・琥珀・赤）を、スラブの調子に合わせて彩度を少し落として使う。

## RGH-911 印刷では Light の配色に切り替える

```text
画面: Dark のスラブ   →   印刷: 白地のスラブ（インクの節約）
```

- ストック。紙に刷るときはインクの量と読みやすさの点で有利だが、画面で確かめた誌面と配布資料の見た目が変わる。PDF を画面で配る用途では Dark のまま刷りたい場合もある。まずは画面と同じ配色で刷り（`RGH-119`）、紙の配布で不満が出たら、印刷の前に外観を選べる案として再検討する。

## RGH-907 表のセルを文節でだけ折り返す

```text
│ カード右上コーナーオーナメント │ ← 1 つの文節が列の最小幅になる
→ 7 列の表が版面からはみ出し、横スクロールになる
```

- ボツ。短いラベルの列だけを 1 行に保ち、それ以外は文節の中でも折り返せるようにした（`DTP-VTPL-110`）。

## RGH-901 独自の記法で雛形を指定する

- ボツ。Lucivo 以外のビューアーではただのコメントになり、指定の意味が失われる。

## RGH-902 要点カード型を 3 列固定・最小幅の自動段数にする

```text
┌────┐ ┌────┐ ┌────┐
│ 01 │ │ 02 │ │ 03 │
└────┘ └────┘ └────┘
┌────┐                 ← 4 個目が 1 つだけ残る（端数）
│ 04 │

```

- ボツ。最小幅の自動段数でも、3 個が 2 列＋1 枚になる端数が出た。項目の数で列を決める方式（`RGH-002`）を採用。

## RGH-146 つながる図（タグと曲線でつなぐ）

```text
┌ STAGE 02  注文の受付から出荷まで ─────────────────────────────┐
│ ┌ 図 1 ────────┐    ┌ 図 2 ────────┐    ┌ 図 3 ────────┐ │
│ │ 注文を受信     │  ┌→Ⓐ在庫を引き当てる│  ┌→Ⓑ出荷を指示する │ │
│ │   ↓           │  ┊ │   ↓           │  ┊ │   ↓           │ │
│ │ 入力は正しい?  │  ┊ │ 決済を実行する │  ┊ │ ピッキングする │ │
│ │   ↓           │  ┊ │   ↓           │  ┊ │   ↓           │ │
│ │ 在庫を引き当てるⒶ┄┘ │ 出荷を指示する Ⓑ┄┘ │ 完了           │ │
│ └───────────────┘    └───────────────┘    └───────────────┘ │
└──────────────────────────────────────────────────────────────┘
  ┄ = 点線の曲線。Ⓐ・Ⓑ = 同じ名前のノードに付く、同じ文字のタグ
```

- ストック。縦に長い図を、書き手がいくつかの図に分けて書いたときに、ビューアーがつなぐ案（#146 の検討で出た）。1 つの章に続けて書いた図で、前の図の終わりと次の図の始まりが同じ名前のとき、図を横に並べ、2 つのノードを同じ色の輪とタグで示し、点線の曲線でつなぐ。専用の記法は使わない（`RGH-901` と同じ方針）。クリックのリンク（Mermaid の `click`）は使わない。
- 試作の結果: 3 つのフローチャート（12 の手順）は、3 列に折り返して読めた。状態遷移図 2 つでは、図ごとに `Fit` の倍率が違って文字の大きさがそろわず、細い段で図がカードからはみ出した。
- 再利用の条件: 作るときは、つなぐ図の倍率をそろえる処理と、曲線の描き直し（幅の変更、`Fit` / `1:1`、`Expand`、遅れて描かれる図、ステージ発表）が要る。スマホの幅では図が縦に積まれるため、タグだけにする。規模が大きいため、#146 とは別の変更要求として扱う。

## RGH-147 画面より長い図で、解説を上端に固定する

```text
┌──────────────────────────────────┐
│ 解説（送っても   ┌ 図 ─────────┐ │
│ 画面の上に残る） │             │ │ ← position: sticky
│                  │  （長い図） │ │
│                  │             │ │
```

- ストック。高さ 2,000px の図でも、図を読み進める間、解説が横に残る。画面に収まる普通の図には効果がない。
- 再利用の条件: 画面より長い図を 2 段組みで見せる場面が増えたとき。今は、解説の上の空きを `18rem` までにして、章を開いたときに解説が見えるようにしている（`DTP-VTPL-060`）。

## RGH-148 長文の章を、広い画面で 2 段組みにする

```text
狭い画面（今のまま）               広い画面（版面の上限を超えたとき）
┌──────────────────┐           ┌──────────────────────────────────────────┐
│ 見出し              │           │ 見出し（全幅）                              │
│ 段落……………………………… │           │ 段落…………………………  ┊ 段落…………………………     │
│ ……………………………………… │    →      │ ………………………………  ┊ ………………………………     │
│ 段落……………………………… │           │ 段落…………………………  ┊ ………………………………     │
│ ……………………………………… │           ├──────────────────────────────────────────┤
└──────────────────┘           │ 表・図・コード（全幅。段をまたぐ）            │
                                   └──────────────────────────────────────────┘
  1 段の字数を 35〜40 字ほどにし、段の高さは画面の高さ以内で区切る
```

- 状態: Issue #233（0.10.4）に起票した。採否は、dtp のラフと試作のゲラで決める。それまでストックとして置く。長文の章で、画面の幅が十分にあるときは 2 段組みにして、1 行の長さを短くし、左右の視線の移動を減らす案（ユーザーのネタ）。
- 今の誌面の幅（事実）: 版面の幅に上限がある（通常表示の `.prose-doc` は `54rem`、Visualモードの `.exhibition-wrap` は `62rem`）。広い画面でも 1 行は伸びず、左右に空きが出る。Visualモードの本文の 1 行は 55〜60 字ほど（1440px の画面のゲラで数えた目安）。つまり、今の課題は「画面が広いと行が長くなる」ことより、「1 行が長めのまま、広い画面の幅を使い切れていない」こと。
- 1 段の字数の目安（35〜40 字）は、本や雑誌の組版の慣習からの推定で、検証した数値ではない。試作のゲラで決める。
- 段組みにする条件（案）:
  - 版面の上限を超える幅の画面（境目は未確定。例: 1600px 以上）で、段落が中心の長文の章だけ。要点カード・手順などの雛形の章と、解説＋図版型（`RGH-005`）の章には使わない
  - 見出し・表・図・コード・ブロック数式・引用を、段をまたいで全幅に置く（CSS の `column-span: all`）か、段の中に収めるかは、一律には決めず、要素ごとに決める（ユーザーの指摘。初期の案は Issue #233 の表）
  - スマホの幅・ステージ発表・印刷では使わない（印刷は 1 章 1 ページの規則 `RGH-119` がある）
- 懸念（採否の前に試作で確かめる）:
  - **上下の戻り**: 画面はスクロールで読むため、段が画面より高いと、左の段の下まで読んでから、右の段の頭へスクロールを戻すことになる。左右の移動は減っても、上下の大きな戻りが増える。段の高さを画面の高さ以内で区切る（小見出しや一定の段落数ごとに段組みを作り直す）か、段の高さが画面に収まる章だけに使う必要がある
  - **段の切れ目**: 段落の途中で段が替わると、読む位置を見失いやすい。段落の途中で割らない（`break-inside: avoid`）と、段の高さが揃わない
  - **検索とスクロールの位置**: 目次からの移動、`J` / `K` の章送り、Split 表示の編集位置への追従（`FR-037`）が、段の中の位置を指せるか
- 似た案との違い: ワンシート・ポスター（`RGH-125`）は、印刷用に章を新聞のように多段に並べる案で、画面の長文の読みやすさが狙いのこの案とは別。

## RGH-913 図の高さが解説の数倍なら 1 段組みにする

- ボツ。6〜8 ノードの普通の図でも、図の高さは解説（2〜3 行）の 5〜9 倍になる。この規則では、ほとんどの章が 1 段組みになり、解説＋図版型（`RGH-005`）が使われなくなる。

## RGH-914 縦長の図の章は段の比を入れ替える

- ボツ。図の段を細くすると、図のカードの操作バーが 2 行に折り返し、等倍より縮む図も出た。解説の行が長くなるだけで、空きは減らなかった。

## RGH-903 常時ループする背景パーティクル・光彩アニメーション

```text
┌──────────────────────────────────────────────────┐
│  ✦  ∘   ✦    （常時浮遊・明滅する背景エフェクト）  │
└──────────────────────────────────────────────────┘
```

- ボツ。操作していない間も常時アニメーションが動くと、技術文書や図版の読解の妨げになり、さらに常時 GPU 再描画が発生して閲覧操作のリアルタイム性（`NFR-006` / `NFR-007`）を損なうため。ユーザーのホバーやクリックに応答するインタラクティブ・スポットライト（`RGH-007`・`008`）を採用。
