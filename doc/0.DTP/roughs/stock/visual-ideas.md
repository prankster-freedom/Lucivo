# ストックのラフ: Visualモードの訴求ポイントのネタ（visual-ideas）

Visualモードの追加訴求ポイント（`AGENTS.repo.md` 5 章）として出したネタを残す。どれも未採用のストックで、採否・優先順位は決めていない。ラフとして、コンセプトを極端に振っている（完全に静的、動的な演出に全振り、特定の使い方に限る、など）。採用するときは、振り幅を製品に合う所まで戻してよい。

## 共通の前提

- **独自の記法を足さない**: 元の Markdown に Lucivo だけの書き方（専用のコメント、専用の属性、専用のコードブロックの言語名など）を求めない。標準の Markdown・Mermaid・YAML フロントマターで書いた文書が、そのまま化けることを条件にする（`RGH-901` をボツにした理由と同じ）。
- **オフライン・ライブラリなし**: ブラウザの標準の機能だけで作る（`NFR-001`, `NFR-008`）。
- **閲覧操作のリアルタイム性を保つ**: 重い処理は、Visualモードへの切り替え・発表の開始・書き出しのときに寄せる（`NFR-006`, `NFR-007`）。
- **動きを減らす設定**: `prefers-reduced-motion: reduce` では、動きを止めた静止の見え方を必ず用意する。

各ネタは、次の項目で書く。

| 項目             | 内容                                       |
| :--------------- | :----------------------------------------- |
| 一言で           | 何が起きるか                               |
| 振った軸         | どの方向に極端か                           |
| 入力             | 文書のどの部分から作るか（独自の記法なし） |
| 静的なコンセプト | 止まった状態の構図（ワイヤーフレーム）     |
| 動的なコンセプト | 時間の流れ（何が、いつ、どれだけ動くか）   |
| 技術の当たり     | 使う仕組みと、既存のコードのどこにつなぐか |
| 難所・未確定     | 採用の前に決めること、試すこと             |
| 見積もり         | 規模・難易度（未検証の概算）               |

ソースのパスは `src/ts/`・`src/css/`・`public/js/stage.js`（発表の演出の部品。グローバルの `LucivoStage`）を指す。

## RGH-120 フロー・シネマ

- **一言で**: ステージ発表で、カメラが図の流れに沿ってノードからノードへ寄っていく。図を 1 枚の絵ではなく、順に語る物語にする。
- **振った軸**: 動的（カメラワーク）。図は描き直さず、見せる範囲だけを動かす。
- **入力**: Mermaid のフローチャート・状態遷移図・シーケンス図。ノードの順番は、図の結線から決める。

静的なコンセプト（1 つのビートの構図）:

```text
┌ シーン（16:9）──────────────────────────────┐
│ ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │  ░ = 沈めた部分（不透明度 25% 前後）
│ ░░░░┌────────┐        ┏━━━━━━━━━━┓░░░░░ │
│ ░░░░│ 前のノード │ ═══▶ ┃ 注目のノード ┃░░░░░ │  注目のノードが画面の中央・幅の 35〜45%
│ ░░░░└────────┘        ┗━━━━━━━━━━┛░░░░░ │  入ってくる矢印だけ光らせる
│ ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │
│                         ● ● ◉ ○ ○ ○   3 / 6 │  右下に、ビートの位置の点
└─────────────────────────────────────────┘
```

動的なコンセプト:

1. シーンに入ると、図の全体が見える（今と同じ）。
2. `→` を押すたびに 1 ビート進む。カメラは 0.7〜0.9 秒かけて、次のノードが中央に来るよう、表示範囲を滑らかに動かす（ease-in-out）。ズームは、ノードの大きさに合わせて 1.6〜3 倍。
3. 進む先の矢印の上を、シグナル・ライトの光が 1 回だけ走ってから、ノードが明るくなる。それ以外のノードと矢印は沈む。
4. 分岐は、図に書いた順に 1 本ずつたどる。合流するノードは、最後の枝が着いたときに 1 回だけ見せる。
5. 最後のビートの次で、カメラが引いて全体を見せ、全部のノードを明るく戻す。その次の `→` で次のシーンへ進む。
6. `←` は 1 ビート戻る。俯瞰（`O`）と幕間（`B`）に入るときは、カメラを全体に戻す。

技術の当たり:

- **順番**: `LucivoStage` の `buildPlan()` / `scheduleGraph()` / `scheduleSequence()` が、シグナル・ライトのために「どのノードに、いつ光が着くか」を既に計算している（`plan.pulses` の `time` と `rect`）。着く時刻の順に並べると、そのままビートの並びになる。
- **カメラ**: SVG の `viewBox` を、全体の値と「ノードの矩形に余白を足した値」の間で補間する（`requestAnimationFrame`）。`viewBox` で寄るのでベクターのまま拡大され、文字がぼけない。縦横比は、表示枠の比に合わせて余白で調整する。
- **沈める**: 注目外のノード・矢印のグループに、不透明度を下げるクラスを付ける。光の層（Canvas）は `layoutFlow()` が SVG の位置に合わせているため、`viewBox` を変えたら配置し直す。
- **進行**: 発表の項目の送り（`show.build` と `applyBuild()`）に、図のビートを項目として足す。ビートの数は `plan` から決まる。
- **動きを減らす設定**: 補間をやめ、ビートごとに表示範囲を切り替えるだけにする。

難所・未確定:

- ノードが多い図（30 以上）は、ビートが多すぎる。サブグラフや深さでまとめる上限（例: 12 ビートまで）を決める。
- `viewBox` の補間中は、光の層の再配置が毎フレーム要る。重ければ、移動中は光を止める。
- 図によっては結線の順が物語の順と合わない。書いた順を優先するか、結線の順を優先するかを、試して決める。

見積もり: 規模は大、難易度は高。

## RGH-121 データ・ライブチャート

- **一言で**: 数値の列を持つ表を見分けて、誌面品質のグラフを自動で添える。発表では、棒が伸び、線が描かれ、数値が数え上がる。
- **振った軸**: 静的（誌面のグラフ）と動的（発表での成長）の両方。入力は、ただの表。
- **入力**: GFM の表。グラフ用の記法は足さない。

静的なコンセプト:

```text
┌ スラブ ────────────────────────────────────────┐
│ STAGE 03  四半期ごとの売上                                │
│ ┌ 表（そのまま残す）──┐  ┌ グラフ（自動で添える）───────┐ │
│ │ 期    売上   前年比  │  │ Q1 ████████░░░░░░  120    │ │
│ │ Q1    120   +8%    │  │ Q2 ███████████░░░  165    │ │
│ │ Q2    165   +12%   │  │ Q3 █████████████░  190    │ │
│ │ Q3    190   +15%   │  │ Q4 ███████████████ 230 ◀最大 │ │
│ │ Q4    230   +21%   │  │                            │ │
│ └───────────────────┘  └────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

- グラフの種類は、表の形から決める。

  | 表の形                                   | グラフ                                               |
  | :--------------------------------------- | :--------------------------------------------------- |
  | 先頭の列が項目、数値の列が 1 つ          | 横棒（値の大きい順には並べ替えない。書いた順を保つ） |
  | 先頭の列が時系列（年・月・四半期・日付） | 折れ線（数値の列が複数なら、列ごとに線）             |
  | 数値の列の合計が 100%（± 1）             | 100% の帯グラフ                                      |
  | 数値の列が 2 つで、単位が違う            | 棒＋折れ線（2 軸）。まずは対象外にしてよい           |

- 色は、スタイルの 4 色（`--vs-c1`〜`--vs-c4`）を系列に当てる。最大・最小の値にだけ、小さな印を付ける。
- 軸の目盛りは最小限（3〜4 本の薄い線）にし、値はグラフの要素に直接添える。

動的なコンセプト:

- **誌面**: グラフは静止。表の行に触れると、対応する棒・点が明るくなり、ほかが少し沈む。グラフ側に触れると、表の行に淡い帯が付く。
- **発表**: シーンの項目の送りに合わせて、棒が左から 0.6 秒で伸び、線が左から右へ描かれる。値は 0 から数え上がる。系列が複数なら、1 系列ずつ。
- **動きを減らす設定**: 最終の状態を最初から表示する。

技術の当たり:

- **見分け**: サニタイズ後の DOM の `table` を調べる（`wrapTables()` の近く）。セルの文字から数値を読む正規表現は、KPI の判定（`METRIC_TITLE_RE`）と時系列の判定（`TIMELINE_TITLE_RE`）が既にあり、流用できる。条件の案: データ行が 2〜24、数値として読めるセルが数値の列の 80% 以上、列の単位がそろう。
- **描画**: SVG を自前で組む（`rect`・`polyline`・`text`）。数式の補足グラフ（`math/plot.ts`）と同じく、部品を `src/ts/` の別のモジュールにする。印刷・PDF にそのまま出る。
- **発表のアニメーション**: 棒は `transform: scaleX()`、線は `stroke-dasharray` と `stroke-dashoffset` の遷移。数え上げは `requestAnimationFrame`。
- **配置**: 表とグラフの並べ方は、解説＋図版型（`RGH-005`）の 2 段組みの仕組みに近い。幅が足りなければ、グラフを表の上に置く。

難所・未確定:

- 誤判定（型番・年号・電話番号の列をグラフにする）を避ける規則。迷ったらグラフにしない。
- グラフを添えない方法が要る（独自の記法は使えない）。画面の操作（スラブごとの切り替え）で持つか、判定を厳しくして不要にするか。
- 負の値、桁の違いすぎる値、単位の混在の扱い。

見積もり: 規模は大、難易度は高。

## RGH-122 マジック・モーフ

- **一言で**: 連続する章の図に同じ名前のノードがあると、シーンを送るときに、そのノードが消えずに次の図の位置へ移動する。図が章をまたいで育つように見える。
- **振った軸**: 動的（連続性）。シーンの切り替えを、切り替えに見せない。
- **入力**: 連続する 2 つのシーンの Mermaid の図。ノードのラベルの文字が同じものを、同じノードとみなす。

静的なコンセプト（前後の図の対応）:

```text
 シーン N（現状）                      シーン N+1（改善後）
 ┌──────┐   ┌──────┐                ┌──────┐   ┌──────┐   ┌──────┐
 │ 受付  │──▶│ 審査  │                │ 受付  │──▶│ 自動判定│──▶│ 審査  │
 └──────┘   └──────┘                └──────┘   └──────┘   └──────┘
     ↑同じ名前        ↑同じ名前              ↑そのまま      ↑新しい      ↑右へ移動
```

動的なコンセプト（シーンの切り替えの 1.2 秒）:

1. 0〜0.2 秒: 前の図の矢印と、次の図にないノードが薄れて消える。
2. 0.2〜0.9 秒: 同じ名前のノードが、前の位置・大きさから、次の位置・大きさへ移動する。本文と見出しは、通常のシーンの入れ替えをする。
3. 0.7〜1.2 秒: 次の図にだけあるノードが、その場で小さく現れて元の大きさになる。矢印が描かれる。
4. 対応するノードが 1 つもなければ、通常の切り替えに戻す。

技術の当たり:

- **対応付け**: 両方のシーンの SVG から、ノードのグループ（フローチャートなら `g.node`）とラベルの文字を集め、文字が同じものを組にする。同じ文字が複数あるときは、出現の順で組にする。
- **動かし方（FLIP）**: 次のシーンを表示した直後に、次の図のノードの画面上の矩形（`getBoundingClientRect()`）を測る。前の図で測っておいた矩形との差を `transform`（移動と拡大・縮小）で打ち消してから、`transform` を外す遷移をかける。SVG の要素への CSS の `transform` は、`transform-box: fill-box` を付けると矩形を基準にできる。
- **つなぎ先**: シーンの切り替えは `applyScene()` / `goToScene()`。切り替えの前に前の図の矩形を記録し、後でアニメーションをかける。光の層は、移動の間は止める（`suspendLights()`）。
- **代案**: ブラウザの View Transitions API（`document.startViewTransition()`）と `view-transition-name` でも近いことができる。ただし、SVG の中の要素に名前を付けられるかと、Firefox / Safari の対応を確かめる必要がある。

難所・未確定:

- ノードの形が前後で違う（四角からひし形）ときの見せ方。大きさだけ補間し、形はフェードで入れ替える案。
- 矢印は対応付けが難しい。補間せず、消して描き直す。
- 図の種類が前後で違うときは対象外にする。
- `Fit` の倍率が前後で違うと、文字の大きさも変わる。拡大・縮小を含めて補間する。

見積もり: 規模は大、難易度は高。

## RGH-123 スピーカー・ビュー

- **一言で**: 発表中に、発表者だけが見る 2 つ目のウィンドウを出す。現在と次のシーン、経過時間、そのシーンの元の文章の全文を表示する。
- **振った軸**: 使い方に限る（発表の本番）。聴衆側の見え方は一切変えない。
- **入力**: 文書そのもの。発表者ノート用の記法は足さない。Visualモードは長い本文を誌面用に組み替えるため、「元の文章の全文」がそのまま台本になる。
- **既存のラフとの関係**: `RGH-106`（発表者用の手元画面。ストック）を具体化したもの。

静的なコンセプト（発表者側のウィンドウ）:

```text
┌ 発表者ビュー ─────────────────────────────────────────┐
│ ┌ 現在のシーン（縮小）──────┐  ┌ 次のシーン（縮小・淡く）┐  │
│ │                          │  │                        │  │
│ │   STAGE 05 …             │  │   STAGE 06 …           │  │
│ └──────────────────────────┘  └────────────────────────┘  │
│  05 / 19   項目 2 / 4                                      │
│ ┌ このシーンの元の文章（大きな文字・スクロール）──────────┐ │
│ │ ここに章の Markdown の本文が、組み替え前のまま出る。     │ │
│ └────────────────────────────────────────────────────────┘ │
│  経過 12:30     このシーン 01:45     残りの目安 08:10      │
└──────────────────────────────────────────────────────────┘
```

動的なコンセプト:

- 聴衆側でシーン・項目を送ると、発表者側が 0.2 秒以内に追従する。発表者側からも送れる（どちらのウィンドウのキー操作でも進む）。
- タイマーは、発表の開始から数える。1 シーンあたりの平均から、残りの目安を出す。
- 発表者側のウィンドウを閉じても、聴衆側の発表は続く。

技術の当たり:

- **2 つ目のウィンドウ**: `window.open()` で同じ `index.html` を、発表者ビューを示す URL のフラグメント（`#speaker`）付きで開く。開いた側は、発表者用のレイアウトだけを描く。
- **同期**: `BroadcastChannel`（同じオリジンのウィンドウ間の通信）で、シーンの番号・項目の番号・文書の文字列を送る。`file://` のページ同士は、ブラウザによってオリジンの扱いが違い、通信できない可能性がある。その場合は、開いたウィンドウへの参照（`window.open()` の戻り値と `window.opener`）と `postMessage()` を使う。
- **状態の出どころ**: `LucivoStage` の `show.index` / `show.build`。`goToScene()` と `applyBuild()` のところで通知を送る。
- **元の文章**: 章ごとの Markdown は、`renderApp()` のトークンの `raw` を `h2` で区切れば得られる（`srcLine` の仕組みが既にある）。
- **画面の割り当て**: Window Management API（`getScreenDetails()`）があれば、聴衆側を外部のディスプレイへ全画面で出せる。なければ、利用者が手でウィンドウを移す。

難所・未確定:

- `file://` での `BroadcastChannel` と `window.open()` の動作を、Chrome / Edge / Firefox の実機で確かめる。
- フォルダから開いた文書の画像（blob URL）は、別のウィンドウでは使えない。発表者側の縮小図は、聴衆側のシーンの写しではなく、文書から描き直す必要がある。
- 残りの目安の出し方（予定の時間を入力させるか）。

見積もり: 規模は中〜大、難易度は中〜高。

## RGH-124 アンビエント・テーマ

- **一言で**: 文書ごとに、その文書だけの配色と表紙の光を自動で作る。4 つのスタイルから選ぶのではなく、この文書のためにデザインされた一点物に見せる。
- **振った軸**: 静的（色）。動きは足さない。
- **入力**: 題名と `tags`（フロントマター）。文書に画像があれば、最初の画像の色。どれも標準の書き方。

静的なコンセプト:

```text
 文書 A（題名「海洋観測の報告」）        文書 B（題名「決算の概要」）
 ┌ 表紙 ───────────────┐              ┌ 表紙 ───────────────┐
 │ ╲ 青緑の光            │              │ ╲ 深い紺と金の光       │
 │   海洋観測の報告       │              │   決算の概要           │
 │ ▬ ▬ ▬ ▬ （4 色の帯）   │              │ ▬ ▬ ▬ ▬ （4 色の帯）   │
 └──────────────────────┘              └──────────────────────┘
   4 色: 青緑・水色・砂色・珊瑚            4 色: 紺・金・灰青・えんじ
```

- 基準の色（1 色）を決め、そこから 4 色を作る。
  - 画像があるとき: 画像の主要な色（最も面積が広く、彩度のある色）を基準にする。
  - 画像がないとき: 題名と `tags` の文字列のハッシュから、色相を決める。同じ文書は、いつ開いても同じ色になる。
- 4 色は、基準の色相から、類似色（± 30°）と補色寄り（+ 150〜180°）を組み合わせ、明度と彩度をそろえる。既存の 4 スタイルの調子（パステル、落ち着いた色など）を、明度と彩度の型として使う。
- 表紙の光（グラデーション）、章番号のバッジ、4 色の帯、図のノードの色が、すべてこの 4 色に連動する。

動的なコンセプト: なし（完全に静的）。スタイルを切り替えたときの色の遷移は、既存のものをそのまま使う。

技術の当たり:

- **色の変数**: Visualモードの配色は `--vs-c1`〜`--vs-c4`（`DTP-003`）に集まっている。5 つ目のスタイルとして、この 4 つの変数を JavaScript から設定するだけで、雛形・バッジ・帯に効く。図の配色（Mermaid のテーマ変数）は、スタイルごとの定義に同じ色を渡す。
- **ハッシュ**: `utils/hash.ts` の `fnv1aHash()` がある。
- **画像の色**: 画像を小さな Canvas（例: 32×32）に描き、`getImageData()` で画素を集計する。色相を 12〜24 個の区間に分け、彩度で重みを付けて、最も多い区間を選ぶ。`file://` の画像は Canvas を汚染して読めないことがあるため、読めなければハッシュに切り替える。フォルダから開いた画像（blob URL）は読める。
- **読みやすさ**: 文字に使う色は、背景とのコントラスト比（WCAG の式）を計算し、3:1（大きな太字）・4.5:1（本文）を下回ったら明度を動かす。Dark では明度の型を切り替える。

難所・未確定:

- どんな色相でも破綻しない明度・彩度の型。黄色・黄緑は、明るい背景で読みにくい。
- 図の描画結果のキャッシュのキーに、配色を含める必要がある（色が変わると描き直し）。
- 利用者が色を選びたい場合の入口（設定に基準の色を 1 つ持つ）。

見積もり: 規模は中、難易度は中〜高。

## RGH-125 ワンシート・ポスター

- **一言で**: 文書の全部の章を、1 枚の大判のポスター（A1 など）に自動で組む。展示パネルや学会のポスターを、Markdown から直接刷る。
- **振った軸**: 完全に静的。動きも操作もない、紙のための誌面。
- **入力**: 文書の全体。題名・`description`・`author` は表紙の情報（フロントマター）から取る。

静的なコンセプト（A1 横）:

```text
┌──────────────────────────────────────────────────────────────────┐
│  題名（特大）                                    著者・日付・タグ  │
│  ▬▬▬▬ デック（description）                                       │
├───────────────┬───────────────────────┬──────────────────────────┤
│ 01 背景        │ 03 方式（主役の章）     │ 05 結果                   │
│ リードの文     │ ┌───────────────────┐ │ ██████ 120               │
│               │ │   大きな図          │ │ ████████ 165             │
│ 02 課題        │ │                   │ │                          │
│ ● 要点         │ └───────────────────┘ │ 06 まとめ                 │
│ ● 要点         │ 04 手順 ①→②→③        │ 大きな引用の一文           │
├───────────────┴───────────────────────┴──────────────────────────┤
│  用語・出典・連絡先（小さな文字の帯）                               │
└──────────────────────────────────────────────────────────────────┘
```

- 読む順は、左上から列ごとに下へ、次に右の列へ（新聞の段組み）。章番号を大きく付けて、順番を示す。
- 最も大きな図を持つ章を主役にし、中央の列に広く置く。図のない短い章は、細い列に積む。
- 文字の大きさは、1〜2 m 離れて読める基準にする（A1 で、本文 24pt 以上、見出し 48pt 以上、題名 96pt 以上）。
- スラブの雛形（要点カード、手順、引用）は、そのままポスターの部品として使う。

動的なコンセプト: なし。画面では、ポスターの全体を縮小して見せるだけ（拡大・縮小とドラッグは、図と同じ操作）。

技術の当たり:

- **用紙**: `@page { size: A1 landscape; margin: 0 }`（A0・A2・B1 なども同じ）。印刷の仕組みは `css/print.css`（`DD-VTPL-130`〜`132`）にあり、ポスター用の `@page` を名前付きで足す。
- **段組み**: CSS Grid。列の数は用紙の向きで決める（横は 3〜4、縦は 2〜3）。章を「重さ」（図の有無と面積、文字数）で採点し、列の高さが均等に近くなるよう、順番を保ったまま列に割り振る（上から詰めていく貪欲法で足りる）。主役の章は 2 列分にする。
- **はみ出し**: 用紙の高さに収まらないときは、全体の文字の倍率（`rem` の基準）を 5% ずつ下げて組み直す。下限（読める大きさ）を下回ったら、収まらない旨を知らせる。
- **画面での確認**: 用紙の大きさの要素を作り、`transform: scale()` で画面に収める。
- **図**: SVG なので、大判でも劣化しない。光の層（Canvas）は刷らない（既存の印刷と同じ）。

難所・未確定:

- 長い文書（10 章以上）は、1 枚に収まらない。収める章を選ぶ規則か、2 枚に分ける規則が要る。
- 列の割り振りで、読む順と見た目の釣り合いが両立しない場合の優先（読む順を守る）。
- ブラウザの印刷の、大判の用紙への対応（PDF として保存は可能。実機のプリンターは環境による）。

見積もり: 規模は大、難易度は高。

## RGH-126 デモリール

- **一言で**: 文書を、30〜90 秒の映像のように自動で再構成して、無人で流し続ける。題名が動き、要点が 1 つずつ大写しになり、図が動く。そのまま動画として書き出せる。
- **振った軸**: 動的な演出に全振り。操作はなく、読むものでもなく、眺めるもの。
- **入力**: 文書の全体。尺は、章の数と項目の数から自動で決める。
- **既存との関係**: 自動進行と待機の演出（`FR-033`、`RGH-116`）は、ステージ発表を自動で送るもの。デモリールは、誌面を見せずに、要素を抜き出して映像のカットとして組み直す点が違う。

静的なコンセプト（カットの種類）:

```text
 カット 1: 題名            カット 2: 章の題        カット 3: 要点の大写し    カット 4: 図
 ┌────────────────┐      ┌────────────────┐     ┌────────────────┐      ┌────────────────┐
 │                │      │ 02             │     │                │      │  ┌─┐   ┌─┐      │
 │   題 名        │      │ ─────          │     │  「一文だけを   │      │  │ │──▶│ │      │
 │   （画面いっぱい）│      │ 課題           │     │    大きく」     │      │  └─┘   └─┘      │
 │                │      │                │     │           2 / 4 │      │  （カメラが動く） │
 └────────────────┘      └────────────────┘     └────────────────┘      └────────────────┘
```

動的なコンセプト（台本の例。全体で 60 秒）:

| 時間        | カット | 動き                                                                                 |
| :---------- | :----- | :----------------------------------------------------------------------------------- |
| 0〜4 秒     | 題名   | 文字が 1 字ずつ下から現れ、4 色の帯が左から走る                                      |
| 4〜6 秒     | デック | `description` が、題名の下にフェードで入る                                           |
| 6〜8 秒     | 章の題 | 章番号が大きく入り、題が横から滑り込む                                               |
| 8〜16 秒    | 要点   | 箇条書きの項目を 1 つずつ、画面いっぱいの文字で 2 秒ずつ。切り替えは、上下のスライド |
| 16〜24 秒   | 図     | 図がある章は、フロー・シネマ（`RGH-120`）のカメラで、主要なノードを 3〜4 個たどる    |
| …           | 章ごとに繰り返す | 1 章あたり 8〜12 秒。長い段落は、最初の 1 文だけを使う                     |
| 最後の 4 秒 | まとめ | 題名に戻り、光が一周して、最初へループする                                           |

- 切り替えは、すべて 1 つの拍（例: 2 秒）の倍数にして、リズムをそろえる。
- 文字は、1 カットに 1 つの文だけ。40 字を超える文は使わない（次の文に譲るか、章の題だけにする）。

技術の当たり:

- **台本**: Visualモードの DOM（`buildVisualStageHtml()` の結果）から、表紙・章の題・箇条書きの項目・引用・図を抜き出し、`{ 種類, 文字, 秒数 }` の配列にする。雛形の判定（`detectSlabTemplate()`）が、章の種類を既に見分けている。
- **再生**: 全画面の専用のレイヤーに、カットごとの要素を作って入れ替える。動きは CSS のアニメーションと、Web Animations API（`element.animate()`）。時間の管理は 1 つのタイムラインに集める（`requestAnimationFrame` と経過時間）。
- **文字ごとの動き**: 文字を `span` に分け、`animation-delay` をずらす。日本語は 1 字ずつ、英語は単語ごと。
- **動画の書き出し**: `navigator.mediaDevices.getDisplayMedia()` でタブの映像を取り、`MediaRecorder` で WebM にする。利用者が共有するタブを選ぶ操作が 1 回要る。`file://` で使えるかは、実機で確かめる。使えなければ、書き出しは見送り、再生だけにする。
- **動きを減らす設定**: デモリールは動きが本体のため、設定が有効なときは、開始の前に確認を出す。

難所・未確定:

- 文の抜き出しの質（どの 1 文を使うか）が、出来を決める。最初の文、太字のある文、短い文を優先する規則を試す。
- 尺の調整（文書が長いと数分になる）。上限を決め、章ごとの項目数を絞る。
- 図のカットは `RGH-120` に依存する。先に `RGH-120` を作るか、図は全体を見せるだけにする。

見積もり: 規模は大、難易度は高。

- **一言で**: 手順書を、勉強会やワークショップの進行役の画面にする。今の手順だけを巨大に見せ、コマンドはその場でコピーでき、進み具合が全員に見える。
- **振った軸**: 使い方に限る（手順書・チュートリアル）。それ以外の文書では、出番がない。
- **入力**: 番号付きリストと、その中や直後のコードブロック。手順型の雛形（`RGH-003`）が見分けている章が対象。

静的なコンセプト:

```text
┌ シーン ─────────────────────────────────────────────────────┐
│  STAGE 04  環境を作る                         手順 3 / 7      │
│  ①──②──❸──④──⑤──⑥──⑦     （済みは塗り、今は大きく、先は淡く）│
│                                                              │

```

- 前後の手順は、上の進み具合の列にだけ出す。本文は見せない（先を読ませない）。

動的なコンセプト:

- `→` で次の手順へ。済んだ手順の番号が塗りに変わり、列の線が次の番号まで伸びる（0.4 秒）。
- 手順に入ると、その手順のタイマーが動く。目安を過ぎても、色は変えない（急かさない）。

技術の当たり:

- **手順の単位**: 手順型のスラブの `ol > li` が 1 つの手順。発表の項目の送り（`show.build`）は、既に `li` を 1 つずつ見せている。違いは、見せた項目を残さず、今の 1 つだけを大きく置き直す点。
- **コードのコピー**: コード・ショーケース（`FR-031`、`.vs-code-copy-btn`）がある。
- **進み具合**: 手順の数と今の番号は、`show.build` から決まる。済みの記録は、文書のハッシュをキーに `sessionStorage` に持つ（再読み込みで戻らないように）。
- **入口**: 発表の開始のときに、文書の章の過半が手順型なら、ハンズオンの見せ方を選べるようにする。または、発表中のキー 1 つで切り替える。

難所・未確定:

- 手順の中に長い説明や複数のコードがあるときの組み方。
- 番号付きリストが入れ子のとき、どの階層を 1 つの手順にするか。
- 参加者側の進み具合の共有（各自の画面）は対象外。進行役の画面だけにする。

見積もり: 規模は中、難易度は中。

## RGH-128 サウンドスケープ

- **一言で**: 発表に、その場で合成する音を付ける。シーンの切り替え、項目の登場、図を伝わる光の到達に、小さな音が鳴る。図の構造が、音の並びとして聞こえる。
- **振った軸**: 感覚（音）。見た目は 1 つも変えない。
- **入力**: 発表の進行と、図の構造。音のファイルは持たない（すべて合成する）。

静的なコンセプト: なし（画面の変化は、発表の操作部に音の切り替えを 1 つ足すだけ）。

```text
 発表の操作部:  [←] [→] [自動] [俯瞰] [ポインター] [幕間] [♪ 音]
```

動的なコンセプト（音の設計）:

| きっかけ             | 音                                                           | 長さ・大きさ                   |
| :------------------- | :----------------------------------------------------------- | :----------------------------- |
| シーンの切り替え     | 低い柔らかな音が 1 つ（鐘を遠くで鳴らしたような減衰）        | 0.6 秒、控えめ                 |
| 項目の登場           | 短く高い音。項目の番号が進むほど、音程が 1 段ずつ上がる      | 0.15 秒、小さく                |
| 図の光がノードに着く | ノードの深さ（図の中の段）に応じた音程の音。分岐は和音になる | 0.2 秒、ごく小さく             |
| 幕間に入る・戻る     | 音が下がって消える・上がって戻る                             | 0.8 秒                         |
| 待機（無人のループ） | ごく低い持続音が、ゆっくり満ち引きする                       | 連続、聞こえるかどうかの大きさ |

- 音階は 1 つに固定する（例: 5 音の音階）。どの組み合わせで鳴っても、濁らないようにするため。
- スタイルごとに音色を変える（パステルは丸い音、クリームは木の音に近い音、など）。
- 既定は切。発表者が操作部かキーで入れたときだけ鳴る。

技術の当たり:

- **合成**: Web Audio API。`OscillatorNode`（正弦波・三角波）と `GainNode` の包絡（立ち上がり 5〜10 ミリ秒、指数的な減衰）。響きは、短い遅延（`DelayNode`）を薄く重ねる。
- **開始の条件**: ブラウザは、利用者の操作の後でないと音を出せない。発表の開始（クリック・キー）で `AudioContext` を作るか `resume()` する。
- **きっかけ**: シーンは `applyScene()`、項目は `applyBuild()`、光の到達は `plan.pulses` の時刻（`drawFlow()` が毎フレーム見ている）。光のループは繰り返すため、鳴らすのはシーンに入って最初の 1 周だけにする。
- **音程**: 光の到達の順（`time`）と、矢印の深さ（`e.depth`）が `buildPlan()` にある。深さを音階の段に当てる。

難所・未確定:

- 音は、好みが分かれ、場に合わないと害になる。既定は切にし、音量を小さく保つ。
- 会場の音響を通すと、小さな音が聞こえないか、大きすぎる。音量の調整が要る。
- 図の光を音にしたとき、情報として伝わるか、ただの飾りか。試して確かめる。

見積もり: 規模は中、難易度は中〜高（作るより、音の質を整えるほうが難しい）。

## RGH-129 ズーミング・マップ

- **入力**: 見出しの階層（`h1`・`h2`・`h3`）。配置は、階層から自動で決める。

静的なコンセプト（全体の地図）:

┌ 地図（全体）──────────────────────────────────────────────────┐
│                         ┌───────────┐                          │
│          ┌──────┐       │           │        ┌──────┐          │
│          │ 01   │       │   題 名    │        │ 03   │          │

1. 発表の開始: 全体の地図が見える（俯瞰）。
2. `→`: カメラが 1.0〜1.4 秒かけて、最初の章へ飛ぶ。動きは、いったん少し引いてから寄る（地図の上を飛ぶ感じを出す）。章が画面いっぱいになる。
3. 章の中の `→`: 小見出しがあれば、さらに寄る。なければ、項目を 1 つずつ見せる（今と同じ）。
4. 次の章へ: カメラが引いて、道に沿って隣の章へ移り、また寄る。聴衆は、今どこにいて、全体のどこへ移ったかを、動きで理解する。
5. 最後: カメラが引いて、全体の地図に戻る。

技術の当たり:

- **配置**: 章（スラブ）を、大きな平面の上に絶対位置で置く。位置は、章の番号から決める（放射なら角度、道なら折れ線の上の点）。大きさは一定にし、小見出しの枠だけ縮小して入れる。
- **カメラ**: 平面の全体を包む要素に `transform: translate() scale()` をかけて動かす。2 つの見え方の間の補間は、移動と拡大を同時に直線で補間すると不自然になるため、拡大率を対数で補間し、途中でいったん引く（"van Wijk の滑らかなズーム"として知られる考え方。厳密な式でなくても、引く量を距離に比例させれば近い見え方になる）。
- **文字のぼけ**: 大きく拡大した `transform` は、ブラウザが低い解像度で描いた絵を引き伸ばすことがある。寄り終わったら、`transform` の拡大をやめて、要素そのものを実寸で置き直す（切り替えは 1 フレームで、見た目は変わらない）。
- **既存との関係**: 俯瞰（ライトテーブル。`openOverview()` / `zoomTile()`）が、シーンを縮小して並べ、選んだものへ寄る動きを既に持っている。ズーミング・マップは、それを発表の主な移動手段にしたもの。
- **描画の負荷**: 画面の外の章は `content-visibility: auto` で描画を省く。図の光は、今いる章だけ動かす。

難所・未確定:

- 章が多い文書（15 以上）の配置。放射では外側が遠くなりすぎる。道（蛇行）のほうが収まる。
- 16:9 の枠（`--stage-aspect-ratio`）と、章の大きさの関係。
- 動きが大きく、酔いやすい。移動の時間と、引く量の上限を、試して決める。動きを減らす設定では、フェードで切り替える。

見積もり: 規模は大、難易度は高。

## RGH-130 スクロール・シンク

- **一言で**: 本文を読み進めると、いま読んでいる文に出てくる言葉と同じ名前のノードが、隣の図の中で光る。文章と図が、読む速さで対話する。発表ではなく、ふだんの閲覧の体験を変える。
- **振った軸**: 動的だが、操作はスクロールだけ。演出のきっかけを「時間」ではなく「読んでいる位置」にする。
- **着想**: 記事を読み進めると横の図版が切り替わっていく、読み物系の Web サイトの見せ方（スクロールに連動した語り）。それを、作り込みなしで、文章と図の言葉の一致だけから自動で起こす。
- **入力**: 本文と 1 つの図を持つ章（解説＋図版型、`RGH-005`）。本文の語と、図のノードのラベルを照合する。

静的なコンセプト:

```text
┌ スラブ（解説＋図版型）─────────────────────────────────────┐
│ 本文（スクロールで流れる）        │ 図（画面に留まる）          │
│                                  │                            │
│  まず「受付」で申請を受け取り…     │   ┌──────┐   ┌──────┐     │
│ ▌次に「審査」へ回します。審査では… │   │ 受付  │──▶┃ 審査 ┃     │ ← いま読んでいる段落に
│  問題がなければ「承認」となり…     │   └──────┘   ┗━━━━━━┛     │    出てくるノードだけ明るい
│                                  │        ░░░░░░░░           │
│  （本文の中の「審査」に淡い下線）   │       ░ 承認 ░（沈む）      │
└──────────────────────────────────┴────────────────────────────┘
```

- 図は、章を読んでいる間、画面の中に留まる（本文だけが流れる）。
- 本文の中の、ノードと同じ言葉には、ごく淡い下線を付ける（リンクには見せない）。

動的なコンセプト:

1. 章が画面に入ると、図が右に留まる。最初は全部のノードが普通の明るさ。
2. 読んでいる位置（画面の上から 40% の高さにある段落）が変わるたびに、その段落に出てくるノードが 0.3 秒で明るくなり、ほかは 60% まで沈む。前の段落のノードから今のノードへ矢印があれば、その矢印を光が 1 回走る。
3. 言葉の一致がない段落では、全部を普通の明るさに戻す（何も強調しない）。
4. 本文の言葉に触れると、対応するノードが光る。ノードに触れると、本文の対応する言葉すべてに印が付く。
5. 章の最後まで読むと、全部のノードが明るく戻る。

技術の当たり:

- **図を留める**: 2 段組みの図の側（`.exhibition-slab-figure`）に `position: sticky`。スクロールするのはプレビュー（`#preview-scroll`）なので、その中で留まる。
- **照合**: 図のノードのラベル（`g.node` の中の文字）を集め、2 文字以上のラベルだけを使う。本文の段落（`p`・`li`）のテキストノードを走査して、ラベルと同じ文字列を `span` で包む。長いラベルを先に照合する（「一次審査」を「審査」より先に）。英語は、大文字・小文字を区別せず、単語の境界で照合する。
- **読んでいる位置**: `IntersectionObserver` で、画面の上から 40% の細い帯（`rootMargin` で指定）に入った段落を取る。スクロールのたびに計算しない。
- **光**: ノードの明暗はクラスの付け外し。矢印を走る光は、シグナル・ライトの仕組み（`LucivoStage` の `plan.edges`）から、該当する矢印 1 本だけを 1 回描く。
- **動きを減らす設定**: 明暗の切り替えだけにし、光は走らせない。

難所・未確定:

- 誤った一致（一般的な短い語がラベルになっている場合）。一致が章の段落の過半に出るラベルは、強調の対象から外す。
- 日本語は単語の境界がないため、部分一致が起きる（「承認」と「未承認」）。長いラベルを優先するだけで足りるかを試す。
- 図が画面より高いときの留め方。

見積もり: 規模は中〜大、難易度は高（照合の質が体験を決める）。

## RGH-131 ソーシャル・カルーセル

- **一言で**: 文書を、SNS に投稿する連続カード（正方形 1:1、縦長 4:5、全画面の縦 9:16）に自動で組み直して、一式を書き出す。1 章が 1〜数枚のカードになる。
- **振った軸**: 使い方に限る（SNS での発信）。完全に静的で、Lucivo の画面の外で見られることだけを考える。
- **着想**: 作り手が、解説を数枚の画像に分けて投稿する連続カードの形式。1 枚に 1 つのことだけを大きく書き、最後に「続きは横へ」と促す。
- **入力**: 文書の全体。分け方は、スラブの雛形から決める。

静的なコンセプト（4:5 の例）:

```text
 1 枚目（表紙）      2 枚目（章の題）    3 枚目（要点 1 つ）   最後（まとめ）
 ┌──────────┐      ┌──────────┐      ┌──────────┐       ┌──────────┐
 │          │      │ 02       │      │   ❶      │       │          │
 │  題 名   │      │ ────     │      │          │       │  題 名    │
 │ （特大）  │      │ 課題     │      │ 要点の   │       │  著者     │
 │          │      │          │      │ 一文を   │       │          │
 │ ▬▬▬▬     │      │          │      │ 大きく   │       │ ▬▬▬▬     │
 │  1/9  →  │      │  2/9  →  │      │  3/9  →  │       │  9/9     │
 └──────────┘      └──────────┘      └──────────┘       └──────────┘
```

- 1 枚に載せるのは、1 つのことだけ（題名、章の題、要点 1 つ、図 1 つ、引用 1 つ）。
- 文字は、スマートフォンの画面で読める大きさ（カードの幅の 1/14 以上を本文の最小にする）。余白は広く取り、四隅の内側 8% には何も置かない（SNS の画面の部品に隠れるため）。
- 全部のカードに、同じ位置で、通し番号と 4 色の帯を入れる。横に並べたとき、帯がつながって見える。
- 図は、カードの幅に収まる大きさで 1 枚に 1 つ。大きな図は、全体の 1 枚と、主要な部分に寄った 1〜2 枚に分ける（寄る範囲の決め方は `RGH-120` と同じ）。

動的なコンセプト: なし（書き出した画像は静止）。Lucivo の画面では、カードを横に並べて、スワイプ（横スクロール）で確かめる。

技術の当たり:

- **カードへの分割**: スラブごとに、雛形に応じて分ける。要点カード型は項目ごとに 1 枚、手順型は 1〜2 手順ごとに 1 枚、リード型と引用は 1 枚、図は 1 枚。長い段落は、最初の 1〜2 文だけを使う。
- **書き出し（PDF）**: 印刷の仕組みを使う。`@page { size: 1080px 1350px; margin: 0 }` のように用紙をカードの大きさにすると、「PDF として保存」で 1 ページ 1 カードの PDF になる。ブラウザの描画そのままなので、文字も図も崩れない。連続カードを PDF で受け付ける投稿先には、そのまま使える。
- **書き出し（画像）**: PNG の連番にするには、DOM を画像にする処理が要る。以前の章の画像化は、SVG の `foreignObject` を使う方式で誌面が崩れ、操作部を外している（`CR-001`）。画像の書き出しは、`CR-001` の作り直しと合わせて考える。それまでは PDF だけにする。
- **画面での確認**: カードを `scroll-snap` の横スクロールに並べる。

難所・未確定:

- 1 枚に収まらない内容の切り方（文の途中で切らない）。
- 縦横比ごとに組み直すか、1 つの比に絞るか。
- 用紙の大きさを `px` で指定した PDF の、各ブラウザでの出方を確かめる。

見積もり: 規模は中〜大、難易度は中〜高。

## RGH-132 ジェネラティブ・カバー

- **一言で**: 表紙に、その文書の構造そのものから生成した抽象画を置く。章の数、文章の量、図のつながりが、線と粒と帯になる。同じ文書からは同じ絵、文書を書き足すと絵も育つ。
- **振った軸**: 静的が基本（1 枚の絵）。写真も素材も使わず、文書だけからキービジュアルを作る。
- **着想**: データや決まりから絵を生成する作品（ジェネラティブ・アート）と、それを表紙や告知の絵に使う作り手の見せ方。
- **入力**: 見出しの木（`h1`・`h2`・`h3`）、章ごとの文字数、図の数とノードの数、題名の文字列（乱数の種）。
- **`RGH-124` との違い**: `RGH-124` は色を決める。こちらは形を決める。組み合わせられる。

静的なコンセプト（3 つの型。スタイルごとに 1 つを当てる）:

```text
 型 A: 年輪                    型 B: 等高線                  型 C: 織物
 ┌──────────────────┐        ┌──────────────────┐         ┌──────────────────┐
 │      ╭────╮       │        │  ～～～～～～～     │         │ ║ ║ ║║ ║  ║ ║║   │
 │   ╭──┤ ●● ├──╮    │        │ ～～～●～～～～～   │         │ ═══╬═══╬════╬═══ │
 │   │  ╰────╯  │    │        │  ～～～～～～●～   │         │ ║ ║ ║║ ║  ║ ║║   │
 │   ╰──────────╯    │        │ ～～～～～～～～    │         │ ═══════╬═════════ │
 │  章 = 弧、長さ = 文字数 │    │ 山 = 章、高さ = 文字数│      │ 縦糸 = 章、横糸 = 小見出し│
 │  粒 = 図のノード    │        │ 点 = 図             │         │ 結び目 = 図          │
 └──────────────────┘        └──────────────────┘         └──────────────────┘
```

- 絵は表紙の背景に、題名の邪魔をしない濃さ（線の不透明度 15〜35%）で置く。題名の周りは、絵を薄くして読みやすさを保つ。
- 色は、スタイルの 4 色（または `RGH-124` の 4 色）。章の順に 4 色を回す。
- 対応が読める必要はない。ただし、決まりは一貫させる（章を足せば弧が 1 本増える）。目次に触れると、対応する弧・山・糸が明るくなり、絵が文書の地図でもあることが分かる。

動的なコンセプト（任意。基本は静止）:

- 表紙が画面に入ったときに 1 回だけ、線が中心から外へ 1.5 秒かけて描かれる。
- 発表の待機（`RGH-116`）の間だけ、線がごくゆっくり呼吸する（太さが ± 10%、周期 8 秒）。

技術の当たり:

- **データ**: 表紙の目次（`buildCoverHtml()` に渡している章の一覧 `agenda`）に、章ごとの文字数と図の数を足す。見出しと図は、描画のときに既に数えている。
- **乱数**: 題名の `fnv1aHash()` を種にした、決定的な擬似乱数（線形合同法などの数行の関数）。`Math.random()` は使わない（開くたびに変わるため）。
- **描画**: SVG で組む（`path` と `circle`）。印刷・PDF・ポスター（`RGH-125`）にそのまま出て、拡大しても劣化しない。型 A は弧（`A` コマンド）、型 B は高さの関数の等高線を折れ線で近似、型 C は直線の格子に揺らぎを足す。
- **描く動き**: `stroke-dasharray` と `stroke-dashoffset` の遷移。
- **負荷**: 絵は、文書の構造が変わったときだけ作り直す（構造のハッシュをキーにキャッシュ）。入力のたびには作らない。

難所・未確定:

- 短い文書（章が 1〜2 個）でも絵として成り立つ決まり。
- 題名の読みやすさとの両立（絵の濃さ、題名の周りの抜き方）。
- 型を増やしすぎない（スタイルごとに 1 つで足りるか）。

見積もり: 規模は中、難易度は中〜高（作るより、絵の質を整えるほうが難しい）。

## RGH-133 タイポグラフィック・ステージ

- **一言で**: 色も、図形も、装飾も、光も使わない。文字の大きさ・太さ・位置だけで演出する、白と黒だけの発表。同梱の可変フォントの太さを、演出の唯一の道具にする。
- **振った軸**: 引き算に全振り。既存の Visualモード（色と光と素材）の正反対。
- **着想**: 巨大な文字と余白だけで構成する、文字が主役の Web サイトやポスターの見せ方。太さが滑らかに変わる可変フォントの動き。
- **入力**: 文書の全体。強調（`**太字**`）を、演出の手がかりにする。

静的なコンセプト:

```text
┌ シーン（白地に黒。Dark は黒地に白）──────────────────────────┐
│                                                              │
│  02                                                          │
│                                                              │
│  課題は、                                                     │
│  手戻り                 ← 強調の語だけ、太さ 900・ほかの 3 倍の大きさ │
│  にある。                                                     │
│                                                              │
│                                              ────  2 / 12    │
└──────────────────────────────────────────────────────────────┘
```

- 使う色は 2 つだけ（地と文字）。アクセント色・帯・バッジ・影・角丸・背景の模様は、すべて外す。
- 階層は、大きさの比（1 : 1.6 : 2.6 : 4.2 のような 1 つの比率の列）と、太さ（細い 200〜300 と、太い 800〜900 の 2 つ）だけで作る。中間の太さは使わない。
- 配置は、左揃えを基本に、1 つの基準線（左から画面の幅の 8%）にすべてをそろえる。
- 箇条書きは、記号を外し、番号を細い大きな数字にする。表は、罫線を横の細い線だけにする。図は、線を黒 1 色・塗りなしにする。

動的なコンセプト:

1. シーンに入ると、文字は全部、細い太さ（200）で、薄く見えている。
2. 項目を送ると、その行だけが、0.5 秒かけて太さ 200 から 700 へ「息を吸うように」太くなる。前の行は 300 に戻る。位置も色も動かさない。動くのは太さだけ。
3. 強調の語は、最後に 900 まで太くなり、同時に大きさが 1 段上がる。
4. シーンの切り替えは、全部の文字が 0.3 秒で細く（100）なって消え、次のシーンが細い状態で現れる。
5. 光のポインターの代わりに、ポインターに近い文字ほど太くなる（距離に応じて 300〜800）。

技術の当たり:

- **可変フォント**: 同梱の Inter・Noto Sans JP・Plus Jakarta Sans は、太さ 100〜900 の可変フォント（`vendor/fonts/fonts.css` の `font-weight: 100 900`）。`font-weight` を数値で遷移させれば、太さが滑らかに変わる（`transition: font-weight 0.5s`、または `font-variation-settings: 'wght' …`）。
- **太さで幅が変わる問題**: 太くすると字の幅が広がり、行の折り返しが動いてしまう。行ごとに、最も太い状態で幅を測って固定する（`inline-block` と `min-width`）か、折り返しを太い状態で決めてから `white-space: nowrap` で行を固定する。
- **入れ方**: 5 つ目のスタイル（`info-style`）として足す。色の変数（`--vs-c1`〜`--vs-c4`）を全部、文字の色と同じにし、装飾の要素（`.vs-card-ornament`、帯、バッジの面）を `display: none` にする CSS が中心。光の層は起動しない。
- **ポインターと太さ**: 文字を行の単位で `span` に分け、ポインターとの距離を `requestAnimationFrame` で 1 フレームに 1 回だけ計算する。対象は、今のシーンの行だけ。
- **図**: Mermaid のテーマ変数を、白と黒だけにした定義を足す。

難所・未確定:

- 日本語の可変フォントは、太さの遷移の描画が重いことがある（字の数が多い）。動かす行を 1 度に 1〜2 行に絞る。
- 図を白黒にしたとき、色で区別していた情報（マインドマップの枝、円グラフ）が失われる。線の種類や模様で補うか、対象の図を絞る。
- 色を使わない制約の中で、コールアウトの種類をどう区別するか（ラベルの文字だけにする）。

見積もり: 規模は中、難易度は中（CSS が中心。行の幅の固定が難所）。

## RGH-134 ボイス・リアクティブ

- **一言で**: 発表者の声に、舞台が反応する。話している間だけ図の光が流れ、声が大きくなると光が強まり、黙ると静まる。間（ま）を取ると、舞台も息をひそめる。
- **振った軸**: 動的で、しかも入力が人の声。操作も台本もなく、その場の語りが演出を動かす。
- **着想**: 音に合わせて映像が動く、ライブの演出や配信の見せ方。それを、発表者の声と、文書の図に当てはめる。
- **入力**: マイクの音量（声の大きさ）だけ。声の中身（言葉）は使わない。文書への書き足しは一切ない。

静的なコンセプト: なし（画面の変化は、発表の操作部にマイクの切り替えを 1 つ足すことと、反応の強さだけ）。

```text
 発表の操作部:  [←] [→] [自動] [俯瞰] [ポインター] [幕間] [🎙 声]
                                                        ▁▂▅▂▁  ← 入れている間だけ、小さな音量の表示
```

動的なコンセプト:

| 声の状態                           | 舞台の反応                                                                   |
| :--------------------------------- | :--------------------------------------------------------------------------- |
| 話している（音量がしきい値より上） | 図の光が流れる。光の速さは一定、明るさと尾の長さが音量に比例する（60〜140%） |
| 強く言い切る（音量の急な山）       | 光が着いているノードの逆光が、1 回だけ強く脈打つ（0.3 秒）                   |
| 間を取る（0.8 秒以上の無音）       | 光が、いま走っている分を走り切ってから止まる。舞台の周りが、ゆっくり少しだけ暗くなる（2 秒かけて 8%） |
| 話し始める                         | 暗さが 0.3 秒で戻り、光が始点から走り出す                                    |
| 長い無音（10 秒以上）              | 通常の明るさに戻し、反応を止める（質疑や移動のときに、暗いままにしない）     |

- 反応は控えめにする。聴衆が「声に合っている」と気付くかどうかの境目を狙う。目立つ音量メーターにはしない。
- 既定は切。発表者がマイクを入れたときだけ働く。

技術の当たり:

- **マイク**: `navigator.mediaDevices.getUserMedia({ audio: true })`。ブラウザが、利用者に許可を求める。音は Web Audio API の `AnalyserNode` に通すだけで、どこにも送らず、録音もしない（スピーカーにもつながない）。
- **音量**: `getFloatTimeDomainData()` で波形を取り、二乗平均の平方根（RMS）を計算する。1 フレームに 1 回。急な変化をならすため、上がるときは速く、下がるときは遅く追従する平滑化（係数を 2 つ持つ）をかける。
- **しきい値**: 会場の雑音に合わせるため、マイクを入れた直後の 1 秒の音量を基準（床）として測り、その 2〜3 倍をしきい値にする。
- **つなぎ先**: 光の描画（`drawFlow()`）の明るさと尾の長さの係数（`LIGHT` の定数を使っている箇所）に、音量の係数を掛ける。止める・走らせるは `startFlow()` / `stopFlow()`。周りの暗さは、発表の背景の重ねの不透明度。
- **`file://` での動作**: `getUserMedia` は安全な場所（HTTPS や `localhost`）を求める。`file://` は、ブラウザによって使える場合と使えない場合がある。使えないときは、切り替えを出さない。

難所・未確定:

- `file://` でマイクが使えるかを、Chrome / Edge / Firefox の実機で確かめる（使えなければ成立しない）。
- マイクを使うことへの抵抗感。録音も送信もしないことを、切り替えのそばに明記する。
- 会場の音響（発表者の声がスピーカーから返る）で、反応が続いてしまう可能性。
- `RGH-128`（サウンドスケープ）と同時に使うと、Lucivo が出した音にマイクが反応する。同時には使えないようにする。

見積もり: 規模は中、難易度は中〜高（作るより、反応の加減を整えるほうが難しい）。

## RGH-135 プレイアブル・ダイアグラム

- **一言で**: 図が、触って動かせるアプリになる。状態遷移図は「画面とボタンのある試作品」に、フローチャートは「質問に答えて進む診断」になる。仕様書を開いたら、仕様が動いている。
- **振った軸**: 文書であることをやめる（アプリにする）。読むものから、操作するものへ。
- **狙う反応**: 「これ、元は Markdown なの？」。図を書いただけで、作っていないはずの動くものが出てくる。
- **入力**: Mermaid の状態遷移図とフローチャート。書き足しは一切ない。図に普通に書く、状態の名前・矢印のラベル・ひし形（分岐）だけを使う。

静的なコンセプト（状態遷移図 → 試作品）:

```text
┌ スラブ ────────────────────────────────────────────────────────┐
│ ┌ 動く試作品 ─────────────┐   ┌ 図（現在地の地図）──────────────┐ │
│ │  ● ● ●                  │   │   [*] ─▶ 下書き ─▶ ┏━━━━━━┓      │ │
│ │                         │   │                    ┃ 審査中 ┃      │ │
│ │       審査中             │   │            ┌───────┗━━━━━━┛───┐  │ │
│ │  （いまの状態の名前を大きく）│   │            ▼                 ▼  │ │
│ │                         │   │          差し戻し            承認   │ │
│ │  ┌──────────┐ ┌───────┐ │   │   （通った道は明るく、いまの状態は光る） │ │
│ │  │ 承認する  │ │差し戻す│ │   └────────────────────────────────┘ │
│ │  └──────────┘ └───────┘ │    たどった道: 下書き → 審査中           │
│ │   ↑ 出ていく矢印のラベルが、ボタンになる │       [最初からやり直す]   │
│ └─────────────────────────┘                                        │
└──────────────────────────────────────────────────────────────────┘
```

静的なコンセプト（フローチャート → 診断）:

```text
┌ 診断 ────────────────────────────────┐
│  質問 2 / 4 前後                       │
│                                      │
│   在庫はある？        ← ひし形のノードの文字が、質問になる
│                                      │
│   ┌────────┐   ┌────────┐            │
│   │  はい   │   │ いいえ  │  ← 矢印のラベルが、選択肢になる
│   └────────┘   └────────┘            │
│                                      │
│   ← 1 つ戻る                          │
└──────────────────────────────────────┘
        ↓ 終点に着くと
┌ 結果 ────────────────────────────────┐
│   発注する          ← 終点のノードの文字が、結果になる
│   たどった道: 受注 → 在庫はある？（いいえ）→ 発注する
└──────────────────────────────────────┘
```

- 図は消さない。図のカードのヘッダーに「動かす」の切り替えを足し、入れたときだけ、図の横（狭いときは上）に操作の面を出す。
- 操作の面は、端末の画面のような角丸の枠に入れ、文書の一部ではなく、別の「もの」に見せる。

動的なコンセプト:

1. 「動かす」を入れると、図の始点（状態遷移図は `[*]` の次、フローチャートは入る矢印のないノード）が、いまの位置になる。
2. ボタンを押すと、図の上で、その矢印を光が 0.4 秒で走り、着いたノードが光る。同時に、操作の面の中身が横へ滑って入れ替わる（0.3 秒）。
3. 分岐でないノード（出ていく矢印が 1 本でラベルがない）は、「次へ」のボタン 1 つにする。フローチャートでは、0.8 秒見せてから自動で進めてもよい。
4. 出ていく矢印のないノードに着くと、終点として、たどった道と「最初からやり直す」を出す。
5. 図のノードを直接押すと、そこへ飛べる（発表で、途中から見せるため）。
6. キーボード: 数字キーで選択肢、`Backspace` で 1 つ戻る。ステージ発表の中でも動かせる（発表者が、聴衆の答えで分岐を選ぶ）。

技術の当たり:

- **図の構造を取る（第 1 案: 描画結果から）**: `LucivoStage` の `buildPlan()` が、シグナル・ライトのために、SVG の矢印の線（`samplePath()`）とノードの矩形（`nodeRects()` / `nearestNode()`）から「どの矢印が、どのノードからどのノードへ行くか」を既に求めている（`plan.edges` の `from` / `to`）。これをそのまま、移動できる先の表として使う。
- **矢印のラベル**: SVG の中のラベル（`.edgeLabel`）は、矢印の途中に置かれる。ラベルの中心に最も近い矢印の線に結び付ける。
- **ノードの種類**: ノードのグループ（`g.node`）の中の図形で見分ける。ひし形（`polygon`）は分岐（質問）。出ていく矢印がないノードは終点。
- **図の構造を取る（第 2 案: Mermaid から）**: Mermaid は、図を解析した結果（ノードと矢印の一覧）を内部に持っている。公開されている範囲で取り出せるなら、位置からの推定より確実。ただし、版によって取り出し方が変わるおそれがあるため、同梱の版（12 系）で確かめてから決める。未検証。
- **光**: 1 本の矢印だけを 1 回走らせる描画は、`drawFlow()` の中の 1 本分を切り出す。常時のループは、動かしている間は止める（`stopFlow()`）。
- **状態**: いまのノードと、たどった道の配列だけを持つ。描き直し（`renderApp()`）で図が作り直されたら、始点に戻す。
- **動きを減らす設定**: 光と滑りをやめ、切り替えだけにする。

難所・未確定:

- 位置からの推定は、矢印が密な図で、矢印とノードの結び付けを誤ることがある。誤ると、押したボタンと違う先へ進むため、シグナル・ライト（誤っても見た目が少し変なだけ）より厳しい正しさが要る。
- 入れ子の状態（複合状態）、並行の状態、サブグラフの扱い。まずは対象外にして、「動かす」を出さない。
- シーケンス図は、分岐がなく、1 本道の再生になる（`RGH-120` のフロー・シネマと役割が重なる）。対象から外す。
- ラベルのない分岐（矢印が複数あるのに文字がない）は、行き先のノードの名前を選択肢にする。

見積もり: 規模は大、難易度は高。

## RGH-136 ミュージアム・ウォーク

- **一言で**: 文書が、歩いて回れる立体の展示室になる。章は壁に掛かった作品、図は照明の当たった大きな展示、題名は入口の壁の文字。矢印キーで歩き、作品を押すと、その前まで歩いていく。
- **振った軸**: 文書であることをやめる（空間にする）。ページも、スクロールも、スライドもない。
- **狙う反応**: 「嘘でしょ、これ Markdown？」。開いた瞬間に、文書ビューアーの画面ではなく、立体の空間が出てくる。
- **入力**: 見出しの階層と、章の中身。配置は、章の順番と雛形から自動で決める。
- **`RGH-129`（ズーミング・マップ）との違い**: あちらは、平面の地図の上をカメラが飛ぶ（上から見る）。こちらは、空間の中に立って歩く（人の目の高さで見る）。

静的なコンセプト（上から見た配置と、歩いているときの見え方）:

```text
 上から見た配置（1 本の回廊。章が左右の壁に交互に掛かる）
 ┌──────────────────────────────────────────────────────────┐
 │ 入口    ▓01▓          ▓03▓          ▓05▓                  │
 │ ┃題┃   ─────────────────────────────────────────▶  出口  │
 │ ┃名┃          ▓02▓          ▓04▓          ▓06▓    ┃まとめ┃│
 └──────────────────────────────────────────────────────────┘

 歩いているときの見え方（1 点透視）
 ┌──────────────────────────────────────────────────────────┐
 │╲                        （天井。暗い）                     ╱│
 │ ╲   ┌──────────┐                        ┌─────────┐    ╱ │
 │  ╲  │ 02 課題   │      ┌────────┐       │ 03 方式  │   ╱  │
 │   │ │ ● 要点    │      │  奥の壁  │       │  ┌──┐   │  │   │
 │   │ │ ● 要点    │      │ （次の章）│       │  │図│   │  │   │
 │  ╱  └──────────┘      └────────┘       └─────────┘   ╲  │
 │ ╱    （床。作品の淡い映り込み）                           ╲ │
 │╱                                           ▫ 見取り図     ╲│
 └──────────────────────────────────────────────────────────┘
```

- 壁は、スタイルの地の色を少し暗くした面。作品（スラブ）は、額のように壁から少し浮かせ、上から照明が当たったように、上が明るく下へ向かって淡く落ちる。
- 床には、作品の淡い映り込みを置く（空間の奥行きを感じさせる、最も効く 1 手）。
- 右下に、小さな見取り図（上から見た配置と、いまの位置と向き）。
- 入口の壁には、題名を、壁に直接描いた大きな文字として置く。出口の壁には、最後の章（まとめ）か、目次。

動的なコンセプト:

1. Visualモードで「歩く」を入れると、通常の誌面が奥へ倒れ込みながら空間に変わる（0.8 秒）。入口の、題名の壁の前に立っている。
2. `↑` / `W` で前へ、`↓` / `S` で後ろへ、`←` `→` で向きを変える。ドラッグでも見回せる。歩く速さは一定で、止まるときに少しだけ滑る。
3. 作品を押す（または `Enter` / `Space` で次の作品へ）と、カメラがその正面まで歩いて、向きを変えて止まる（1.0〜1.5 秒）。正面に立つと、作品が画面いっぱいになり、普通に読める・文字を選べる・図の光が流れる。
4. 正面に立っている間の `→` は、次の作品へ歩く（発表として使える。1 作品 = 1 シーン）。
5. `Esc` で、空間が手前へ起き上がって、通常の誌面に戻る。

技術の当たり:

- **立体**: CSS の 3D 変形だけで作る（WebGL もライブラリも使わない）。外側の要素に `perspective`（900〜1200px）、空間の全体を包む要素に `transform-style: preserve-3d`。壁・床・作品は、それぞれ `transform: translate3d(…) rotateY(…)` で空間に置いた普通の `div`。作品の中身は、既存のスラブの DOM をそのまま入れる（描き直さない）。
- **カメラ**: カメラを動かす代わりに、空間の全体を逆に動かす。カメラの位置 `(x, z)` と向き `yaw` に対して、空間の要素に `rotateY(-yaw) translate3d(-x, 0, -z)` に当たる変形をかける。`requestAnimationFrame` で、キーの状態から位置と向きを更新する。
- **作品の前まで歩く**: 作品ごとに「正面の立ち位置と向き」を決めておき、いまの位置から補間する。向きは、回る量が小さいほうへ回す。
- **文字のぼけ**: 3D の変形の中の文字は、ぼけて描かれることがある。正面に止まったら、その作品だけを、変形のない普通の要素として画面の中央に重ねて表示する（見た目は同じ位置・大きさにそろえる）。歩き出すときに、空間の中の作品に戻す。
- **映り込み**: 作品を上下に反転した写しを、床の面に、不透明度 8〜12% とぼかしで置く。重ければ、写しではなく、作品の色の淡いグラデーションだけにする。
- **描画の負荷**: 視界の外と、遠い作品は `visibility: hidden` にする（カメラの位置と向きから、前方の一定の距離だけを見せる）。図の光（Canvas）は、正面に立っている作品だけ動かす。
- **発表との関係**: 作品の順番は、発表のシーンの順番（`collectScenes()`）と同じ。発表の操作（次へ・前へ・俯瞰）を、歩く動きに読み替える。
- **動きを減らす設定**: 歩く動きをやめ、作品から作品へ、フェードで切り替える。

難所・未確定:

- 多くのスラブを 3D の変形の中に置いたときの描画の速さ（特に、影やぼかしのあるスラブ）。見せる数を絞っても足りなければ、遠い作品を画像の代わりの単純な面に置き換える。
- 酔いやすさ。視野の広さ（`perspective` の値）、歩く速さ、向きを変える速さを、試して決める。
- 高さが違う作品（長い章）の掛け方。高さの上限を決め、超える章は 2 枚に分ける。
- 見て驚く効果は大きいが、読む効率は下がる。読むための誌面を置き換えるものではなく、見せ場（展示、発表の導入）のための切り替えとして位置づける。

見積もり: 規模は大、難易度は高。
