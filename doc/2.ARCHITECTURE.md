# アーキテクチャ設計書 (2.ARCHITECTURE.md)

## 1. はじめに

本書は本リポジトリで管理する **Lucivo Markdown Presenter — Exhibition-Grade Markdown Viewer —** のアーキテクチャ設計を記述する。今後の増分開発（`swe2`）に伴い更新する。

設計の判断は、要求仕様書の [1.1 プロダクトコンセプト](1.SRS.md#11-プロダクトコンセプト) に従う。

- **高速モード**: 軽快さを最優先する（`NFR-006`）。起動時に読み込むものや、入力のたびに行う処理を増やすときは、その費用を評価し、必要になるまで遅らせる・結果を使い回すなどの方法を先に検討する。
- **Visualモード**: 見た目の品質を優先する（`NFR-007`）。Visualモードへの切り替え時の描画や、Publishing の操作（画像・HTML の書き出しを含む、発表用に整える操作全般）の処理が重くなるのは許容する。ただし、スクロール・表示倍率の切替・拡大表示などの閲覧の操作は、即座に反応させる。

## 2. 制約と利用技術

- **動作環境**: モダン Web ブラウザ（クライアントサイド完結、`NFR-001`）
- **構成**: Vanilla HTML / CSS / JavaScript（ビルドステップなしでもそのまま配信・実行可能）
- **同梱のライブラリ（`public/vendor/`、`NFR-008`）**:
  - Marked `18.1.3`（Markdown トークナイズ・パース）
  - DOMPurify `3.4.17`（HTML サニタイズ、`NFR-003`）
  - Mermaid `12.3.0`（ダイアグラム SVG 生成。図の中の数式は Mermaid に同梱の数式機能で MathML として描画する）。文書に図が初めて現れたときに読み込む
  - KaTeX `0.19.1`（本文の TeX 数式の描画、`FR-010`。JavaScript と CSS）。文書に数式が初めて現れたときに読み込む
- **同梱のライブラリの版の方針**: 本番利用に推奨される最新の版、またはその 1 つ前の版を使う（swe2 スキルの「依存関係の版の管理」）
  - DOMPurify は、[SECURITY.md](https://github.com/cure53/DOMPurify/blob/main/SECURITY.md) で修正の対象を最新のリリースだけとしているので、最新の版を使う
  - Marked、Mermaid、KaTeX は、リリースポリシーが公開されているかを確認していない
- **フォント**: Inter、Plus Jakarta Sans、Noto Sans JP、JetBrains Mono を `public/vendor/fonts/` に同梱する。
- 同梱の設計は [offline.md](3.sw_design_notes/features/offline.md) を参照する。
- **Tailwind CSS**: 使っているクラスだけを [tools/build-tailwind-css.cjs](../tools/build-tailwind-css.cjs) で事前に生成した `css/tailwind.css` を読み込む。Tailwind のクラスを追加・変更したら、このスクリプトで作り直す
- 背景（遅延読み込みと Tailwind の事前生成）: 起動の軽快さ（`NFR-006`）のため。Tailwind の CDN 版はページを開くたびにブラウザ内で CSS を生成し、Mermaid・KaTeX は図や数式がない文書でも読み込まれていた。事前生成の CSS はリポジトリに含めるため、ビルドなしで動かす前提（`NFR-001`）は保たれる

## 4. 主要な設計判断

### 4.1 ファイルの読み込みと保存（`FR-006`, `FR-007`, `FR-013`, `FR-014`, `FR-044`）

- ブラウザのファイル選択（`<input type="file">` と `FileReader`）で読み込む。`index.html` を `file://` で直接開いた場合も動作させるため（`NFR-001`）。
- 保存は、エディタの内容を `Blob` にしてダウンロードする（既存の `downloadBlob()`）。File System Access API による上書きは、対応するブラウザが限られるため使わない。
- フォルダを開く（`FR-044`）ときは、File System Access API（`showDirectoryPicker()`）があればそれを使い、選んだフォルダのハンドルを IndexedDB に覚える（次回は読む許可だけを求める）。ないブラウザ・使えないときは `<input webkitdirectory>` を使う。どちらも、フォルダの中のファイルを `getFile(path)` で読む同じ形（`openedFolder`）にそろえ、一覧と相対パスの画像の処理は方式によらない。読むだけで、フォルダの中は書き換えない。
- 読み取り専用は、エディタの `textarea` の `readOnly` 属性で実現する。エディタの内容を変える機能（テスト用のボタンなど）も、読み取り専用の間は使えないようにする。
- 採らなかった案: 起動時に `fetch('./notation_sample.md')` で自動読み込みする案。`file://` ではブラウザの制約で読み込めず、開き方によって動作が変わるため。
- 詳細は [file-loading.md](3.sw_design_notes/features/file-loading.md) を参照する。

### 4.2 図の描画先と SVG 内の id（`FR-003`, `FR-008`, `NFR-004`）

- 表示していない側のプレビュー（高速モード / Visualモード）は、描画のたびに空にする。両方に図を残すと、`data-stage-index` と SVG 内の id が DOM 上で重複し、描画結果の書き込み先や、矢じり・グラデーションの参照先が非表示側に向くため。
- Mermaid はシーケンス図の矢じり（`#arrowhead` など）や ER 図の端点を、図をまたいで同じ id で出力する。SVG の後処理で、SVG 内の id を SVG ごとに一意な名前に置き換える。
- 詳細は [diagram-rendering.md](3.sw_design_notes/features/diagram-rendering.md) を参照する。

### 4.3 図種ごとの装飾の範囲（`FR-008`）

- Visualモードのノード装飾（形・塗りの置き換え）は、flowchart・状態遷移図・シーケンス図に限る。その他の図種は、Mermaid の配色変数にスタイルごとの配色を渡して描画し、SVG の構造には手を加えない。
- 背景: ノード装飾は `g.node` などの要素を前提にしており、クラス図など他の図種の同名要素に適用すると、図の構造が崩れるため。
- Visualモードのカード背景は、外観（Light / Dark）に合わせて切り替える。Dark では、背景の上に直接描く線・文字を明るくし、装飾したノードの塗り（色付きの図形・白いカード）とその上の文字はそのまま使う（`DD-DIAG-024`）。
- Mermaid の `securityLevel` は `strict` とし、図の中の HTML タグとクリック時のスクリプト呼び出しを無効にする（`NFR-003`）。Mermaid が生成する SVG は DOMPurify のサニタイズの対象外のため。

### 4.4 Markdown 要素の表示（`FR-009`）

- 事前生成の Tailwind CSS（`css/tailwind.css`）の Preflight と `style.css` の全要素リセット（`* { margin: 0; padding: 0; }`）により、ブラウザ標準の要素のスタイルは初期化される。Markdown から生成する要素（見出し、リスト、リンク、コード、引用、表、水平線、標準の HTML 要素）の表示は、すべて `style.css` で定義する。
- 高速モード（`.prose-doc`）と Visualモードの本文（`.exhibition-slab`）は、同じ要素スタイルを共有し、色は Light / Dark のデザイントークン（CSS 変数）から取る。Visualモードの本文の背景（スラブ）は、図のカードと異なり、外観に合わせて Light / Dark で切り替わるため。
- 採らなかった案: Tailwind の Typography プラグイン（`prose` クラス）を使う案。プラグインは独自の文字サイズ・余白・配色を持つため、既存の `.prose-doc` の組版（`h1`・`h2`・表）と重複する。また、Light / Dark のトークンやパレット（`--accent`）と連動させるには、結局すべての色を上書きする必要があるため。
- 詳細は [markdown-typography.md](3.sw_design_notes/features/markdown-typography.md) を参照する。

### 4.5 数式の描画（`FR-010`, `NFR-003`）

- 本文の数式は、Marked の拡張で `$…$` / `$$…$$` を数式の置き場所（TeX の原文を属性に持つ `span` / `div`）に置き換える。DOMPurify でサニタイズした後に、置き場所へ KaTeX で描画する。
- 背景: KaTeX の出力（MathML と、`style` 属性を多用する HTML）をサニタイズにかけると、必要な要素・属性が削られて崩れる。サニタイズ後に KaTeX が自身で安全に生成した要素を入れることで、`NFR-003` を保ったまま正しく表示する。KaTeX は信頼できない入力を前提とした設定（`trust: false`、既定）で使う。
- 置き場所の中身は TeX の原文とし、KaTeX を読み込めない場合は原文がそのまま表示される。
- 図の中の数式は、Mermaid 自身の数式機能に任せる。Mermaid は数式を MathML として出力するため、KaTeX の CSS に依存しない。
- KaTeX の描画結果は TeX ごとにキャッシュし、入力のたびに描画し直さない。
- HTML エクスポートはページ全体を書き出すため、`<head>` の KaTeX の CSS の読み込みも含まれる。

### 4.6 図の表示倍率（`NFR-005`）

- `Fit` は図を表示枠の幅に合わせるが、図の中の最も小さい文字が表示上 10px 未満になる縮小はしない。縮小の下限は、図を描画した後に図の中の文字の大きさを調べて、図ごとに決める。計算結果は描画結果のキャッシュのキーごとに保存し、キャッシュから表示するときは計算し直さない。
- 小さな図は、元の大きさの 1.5 倍までしか拡大しない。枠の幅まで拡大すると、文字が大きすぎる印象になるため。
- 背景: ノードの多い図や横長の図（ガント、ジャーニー、タイムラインなど）は、幅に合わせると文字が 7px 前後まで縮み、判読できなかった。
- 採らなかった案: 縮小率の下限を固定値にする案。図種によって Mermaid が使う文字の大きさが異なり（10〜16px）、固定値では判読できない図と、不要に横スクロールになる図が出るため。

### 4.7 YAML フロントマター（`FR-011`, `NFR-003`, `NFR-006`）

- `renderApp()` で、Marked に渡す前に文書の先頭のフロントマターを切り出す。本文は残りの部分だけを Marked に渡すため、フロントマターが水平線や段落として描画されることはない。
- 表示するときは、YAML を行ごとにエスケープし、キー・値・コメントを `span` で色分けした HTML を作る。この HTML は本文の HTML の先頭に付け、本文と一緒に DOMPurify でサニタイズする（`NFR-003`）。Visualモードでは、本文と同じくスラブの中に入る。
- YAML の解析ライブラリは使わず、行単位の簡易な色分けにとどめる（`NFR-006`、`FR-011` の採らなかった案）。
- 詳細は [front-matter.md](3.sw_design_notes/features/front-matter.md) を参照する。

### 4.8 図ごとの矢印の形状（`FR-012`）

- 矢印の形状は、図の番号ごとに `state.curveByIndex` に保持し、その図を描画するときだけ Mermaid の `flowchart.curve`・`state.curve`・`class.curve` に渡す。描画結果のキャッシュのキーにも、その図の形状を含める。
- 形状を選べる図かどうかは、Mermaid のコードの先頭のキーワード（`flowchart` / `graph`、`stateDiagram`、`classDiagram`）で判定する。Mermaid `12.3.0` で `curve` の設定が効くのは、この 3 つの図種のため（ER 図は効かない）。
- 選択の UI は図のカードのヘッダーに置く。選んだ図だけを描き直す（他の図はキャッシュから表示する）。
- 詳細は [edge-style.md](3.sw_design_notes/features/edge-style.md) を参照する。

### 4.9 Visualモードの自動 2 段組みレイアウト（`FR-015`, `NFR-005`, `NFR-007`）

- `buildVisualStageHtml()` で各スラブを組み立てるとき、スラブ内に本文要素が 1 つ以上あり、かつ図のスロット（`.lucivo-slot`）がちょうど 1 つある場合は、見出し（`h2`）とフロントマターを除く要素を左カラム（`.exhibition-slab-prose`）と右カラム（`.exhibition-slab-figure`）に分けた 2 段組み構造（`.exhibition-slab-split`）で出力する。
- 図を描画して `applyReadableFit()` で文字サイズ下限（10px）に基づく `min-width` を反映した後、2 段組みの右カラム内で図の表示枠（`.exhibition-viewport`）に横スクロールが発生しているか（`scrollWidth > clientWidth + 1`）を調べ、はみ出している場合はそのスラブに `.is-stacked` を付けて 1 段組み（全幅）にフォールバックする。
- 背景: `scrollWidth` と `clientWidth` による判定は `getComputedStyle` を呼ばずに済むため、キャッシュ再描画時の軽快さ（`NFR-006`、`TC-PERF-002`）を損なわず、かつ表示モード切替（`Split` / `Canvas`）や画面幅に応じた実際のカラム幅と `NFR-005` の最小幅を正確に突き合わせられる。
- 詳細は [diagram-rendering.md](3.sw_design_notes/features/diagram-rendering.md) 6 章を参照する。

### 4.10 Visualモードの記述パターン別の雛形と動的ステージ演出（`FR-016`, `FR-017`, `FR-020`, `FR-021`, `NFR-006`, `NFR-007`）

- `buildVisualStageHtml()` でスラブを組み立てるとき、スラブの本文要素（`h2` とフロントマターを除くスラブ直下の要素）の種類・数・文字数から雛形を 1 つ選び、スラブに `.vs-tpl-<雛形>` を付ける。雛形に必要な要素の組み替え（段落のまとまり、カードの題の切り出し、項目数の付与、ベクター装飾素材用の要素 `.exhibition-hero-emblem`・`.vs-card-ornament`・`.vs-step-chevron` の付与）も、このときに DOM の上で行う。見た目は `style.css` の `.vs-tpl-*` と `.vs-*` のクラスで定義する。
- 判定はタグ名と `textContent` の長さだけで行い、`getComputedStyle` や大きさの計測は使わない。Visualモードの描画のたびに行っても軽く、キャッシュからの再描画（`TC-PERF-002`）の条件を崩さない。高速モードでは判定しない。
- 雛形の配色とベクター装飾素材（`assets/motifs/` の `AST-005`〜`008`）の塗りは、`.exhibition-wrap` に付けるスタイルのクラス（`.vs-theme-<スタイル>`）が定義する CSS 変数（`--vs-c1`〜`--vs-c4`）と CSS `mask-image` から取る。図の描画結果のキャッシュのキーは変えない（雛形は図の SVG に影響しないため）。
- 手順型の横並び・縦並びは、版面（`.exhibition-wrap`）の幅に対するコンテナクエリで切り替える。画面の幅ではなく版面の幅で決めることで、`Split` 表示の狭いプレビューでも詰まらない。
- **インタラクティブ・スポットライト（`FR-017`）**: 要点カード（`.vs-points > li`）、手順ステップ（`.vs-steps > li`）、およびスラブ見出しのバッジ（`.exhibition-num-badge`）のクリックは、`#visual-stage-container` へのイベント委譲と `Escape` キーリスナーで処理し、DOM クラスの付け替え（`.is-spotlight`, `.is-reached`, `.is-stage-focused`）だけで視覚状態を遷移させる。`renderApp()` の再実行や `getComputedStyle` を伴わないため、大画面での講演中も即座に反応する。
- 背景: 雛形の判定を Marked のトークンの段階で行う案も考えたが、スラブの分割（`h2` ごと）と 2 段組みの判定（`FR-015`）が DOM の上で行われているため、同じ場所で判定するほうが、判定の順序（`DTP-VTPL-001`）を 1 か所で管理できる。
- **表紙と誌面の表（`FR-020`, `FR-021`）**: `buildVisualStageHtml()` は、`renderApp()` から受け取ったフロントマターの YAML の原文から表紙に使う値（`title`・`description`・`tags`）だけを読み取り（`readCoverMeta()`）、スラブを組み立てながら集めた章の番号と題とあわせて表紙を組む（`buildCoverHtml()`）。表は、スラブに分ける前の DOM の上で列の種類（数値の列・短いラベルの列）をセルの文字から判定してクラスを付ける（`markTableColumns()`）。どちらも計測をしないため、雛形と同じく描画の軽さを保つ。目次から章への移動は、スポットライトと同じく `#visual-stage-container` へのイベント委譲で処理する。
- 背景（YAML の読み取り）: YAML の解析ライブラリは読み込まない。表紙に要るのは先頭の列の 3 つのキーだけで、ライブラリを足すと起動時の読み込みが増える（`NFR-006`）。入れ子のキーや複雑な書き方は読まず、表紙のその要素を出さないだけにする。
- 詳細は [visual-templates.md](3.sw_design_notes/features/visual-templates.md) を参照する。デザインの仕様は [0.DTP/features/visual-templates.md](0.DTP/features/visual-templates.md) を正とする。

### 4.11 Visualモードの舞台演出（`FR-018`, `FR-019`, `FR-022`, `FR-023`, `NFR-006`, `NFR-007`）

- **別ファイルの遅延読み込み**: 舞台演出は `js/stage.js` に置き、`loadLibrary('stage')` で Visualモードの描画時に初めて読み込む。高速モードの起動に読み込むものを増やさない（`NFR-006`）。
- **光は SVG の外の Canvas に描く**: 図の表示枠に Canvas を 2 枚足し、図の背面に光輪とノードの発光、前面に白熱の芯を描く。SVG には何も足さない。
- **図の構造を読み取る**: 線の端点とノードの矩形を座標で照合して接続を求め、根から下流へ届く順に光の出発の時刻を決める。Mermaid の出力の `id` の形式に依存しない。計算は図が初めて画面に入ったときに 1 回だけ行う。
- **ステージ発表は既存の DOM を使う**: シーンの切り替えは、描画済みのスラブの表示を切り替えるだけとする。図を描き直さないため、ページ送りが待たされない（`NFR-007`）。誌面の拡大は `rem` の基準を画面の幅に比例させて行う。
- **俯瞰も既存の DOM を使う（`FR-022`）**: 俯瞰では、すべてのシーンの要素を表示し、それぞれを `transform: scale()` で縮小して格子に並べる。縮小図を別に描かない。全画面と縮小図の間の動きは、Web Animations API で `transform` だけを補間する。俯瞰の間は光の開始を止める（`startFlow()` を通さない）。
- **ポインターはレイアウトを読まない（`FR-023`）**: マウスの位置を覚えておき、`requestAnimationFrame` で 1 フレームに 1 回、CSS 変数と `transform` を書き換える。要素の大きさ・位置を読まないため、マウスの動きでレイアウトの計算が起きない。
- 背景（Canvas）: 以前の演出は SVG の中に線を足して CSS で動かしていた。この方式には 3 つの問題があった。(1) 線の太さが一定で、尾が細くなる光を作れない。(2) 図の SVG が毎フレーム再描画される。(3) SVG の外の CSS が効かない PNG / SVG の書き出しで、線が黒い塗りのくさび形になった。Canvas ならこの 3 つを同時に解決でき、加算の合成で Dark の光も本物に近づく。
- 採らなかった案: SVG のフィルターでぼかす案（`RGH-904`）。シーンごとに図を描き直す案（ページ送りが待たされるため）。俯瞰の縮小図を画像にする案（`RGH-109`。開くまで待たせるため）。
- 詳細は [stage-show.md](3.sw_design_notes/features/stage-show.md) を参照する。デザインの仕様は [0.DTP/features/stage-show.md](0.DTP/features/stage-show.md) を正とする。

### 4.12 Markdown の後処理による記法の拡張と、編集位置への追従（`FR-034`, `FR-035`, `FR-037`, `NFR-006`）

- **記法の拡張は構文解析の後の DOM で行う（`FR-034`）**: GitHub のアラート記法は、Marked の標準の引用として解析させ、サニタイズ後の DOM で、最初の段落がマーカーで始まる `blockquote` だけをコールアウトの `div` に置き換える。Marked の拡張（トークナイザー）を足さないため、Marked の版を上げても影響を受けにくい。高速モードと Visualモードで同じ関数を使う。
- **雛形の判定は要素と文字だけで行う（`FR-035`）**: 定義リスト型も既存の雛形と同じく、`detectSlabTemplate()` で要素の種類と文字（`textContent`）だけを調べる。レイアウトを計測しない。
- **見出しの行の位置は構文解析の結果から求める（`FR-037`）**: `renderApp()` で Marked の字句解析の結果（最上位のトークン）の `raw` の改行を数え、見出しのトークンに元の行番号を持たせる。見出しの描画（Marked の `renderer.heading`）で、その行番号を `data-src-line` 属性として出力する。コードブロックの中の `#` を見出しと誤らず、Visualモードで章に組み替えた後も属性は見出しの要素に残る。カーソルの移動のときは、カーソルの前の改行を数えて、属性を持つ要素を前から引くだけにする。
- 採らなかった案（`FR-037`）: プレビューの見出しを先頭から数えて元の見出しと対応づける案。HTML で書いた見出しや、Visualモードの表紙に移した `h1` で数がずれる。
- 詳細は [markdown-typography.md](3.sw_design_notes/features/markdown-typography.md)（`DD-MD-021`, `DD-MD-022`）、[visual-templates.md](3.sw_design_notes/features/visual-templates.md)（`DD-VTPL-019`, `DD-VTPL-032`, `DD-VTPL-033`）、[diagram-rendering.md](3.sw_design_notes/features/diagram-rendering.md)（`DD-DIAG-060`〜`062`）を参照する。

### 4.13 印刷・PDF の配布資料（`FR-036`, `NFR-006`, `NFR-008`）

- **印刷は CSS の `@media print` だけで行う**: 画面の DOM はそのまま使い、刷らない部品を隠し、スクロール枠の高さの制限を外し、改ページを指定する。印刷の前に DOM を作り直さないため、画面と同じ誌面が刷られ、印刷のための処理が画面の操作の速さに影響しない。
- **用紙の向きは名前付きページで切り替える**: Visualモードのスラブと表紙にだけ名前付きページ（`page: lucivo-visual`、A4 横）を指定し、高速モードは既定のページ（A4 縦）で流す。
- **光の演出の層（Canvas）は刷らない**: 時刻で変わる光は紙では意味を持たず、刷る瞬間の位置が毎回変わるため。
- 採らなかった案: PDF を生成するライブラリを同梱する案（ファイルの大きさと、誌面を再現する手間のため）。
- 詳細は [visual-templates.md](3.sw_design_notes/features/visual-templates.md)（`DD-VTPL-130`〜`133`）を参照する。

### 4.14 GitHub Pages の公開とプレビュー分離（`.github/workflows/deploy.yml`）

- **公開用 URL（本番）**: `https://prankster-freedom.github.io/Lucivo/` には最新リリースタグ（`lucivo-v*`）に対応する GitHub Release の Web 版成果物（`Lucivo-v<版>-web.zip`）を展開して配置し、リリースタグの push または GitHub Release 公開時に更新する。`-web.zip` がない過去のリリースでは従来の `Lucivo-v<版>.zip` を、それもなければタグからのフォールバックビルドを使う。これにより公開用 Web 版とスタンドアロン版（ZIP）のビルド番号が一致し、開発途中の `main` 反映や Canary デプロイで本番 URL のビルド番号が変動しない。
- **テスト用 URL（プレビュー）**: `https://prankster-freedom.github.io/Lucivo/preview/` には `main` ブランチの最新 `public/` を配置し、`main` への push（および `Self Approve` / `Canary Auto Merge` 完了）時に更新する。`public/` 内のアセット参照はすべて相対パス（`./`）のため、サブディレクトリでも同一構成で動作する。

### 4.15 配布先（channel）とビルド（`tools/build-app.cjs`、`.github/workflows/`）

Web 版の配布物（`public/`）とスタンドアロン版の配布物（`dist/`）を別のフォルダに分け、中身を変えられるようにする。Web 版だけで試す機能（発表モードの試験提供など）を、スタンドアロン版に入れないための土台である（`NFR-001`、`NFR-006`）。この節では分ける仕組みを決める。中身の分け方（どの発表モードを入れるか）は 4.16 で決める。

| 配布先        | 出力先                    | 用途                                   | 検査                 |
| :------------ | :------------------------ | :------------------------------------- | :------------------- |
| `web`（既定） | `public/`（コミットする） | 公開用 URL・テスト用 URL（4.14）、`Lucivo-v<版>-web.zip` | Web 版の E2E（手元のサーバーで配る） |
| `standalone`  | `dist/`（git 管理外）     | `Lucivo-v<版>.zip`（利用者が選ぶ ZIP） | `file://` で開く E2E |

- **ビルド**: `node tools/build-app.cjs --channel standalone` は、`dist/` を作り直し、`public/` のすべてを写したあと、ビルドの出力（`app.js`・`style.css`・モードと遅延読み込みの JS）だけを `dist/` に上書きする。`public/` には触らない。`LUCIVO_VERSION_OVERRIDE` は `dist/` の出力にそのまま効く。写すときに除くファイルの一覧は、発表モードの登録表から作る（4.16 `ARC-MODE-002`）。
- **`dist/` を git 管理外にする**: ビルドの結果をコミットすると、同じ内容が `public/` と二重に残り、更新し忘れの元になるため。
- **テストの前に `dist/` を作る**: `npm test` の `pretest` で `build:standalone`（`--prod`）を実行する。手元でも CI（`e2e.yml`）でも、検査する `dist/` が必ず今のソースから作られる。`e2e.yml` の `build:prod`（`public/` 用）は、Web 版のテストが使うため残す。`node tests/e2e.cjs <TC ID>` の直接実行では `pretest` が走らないため、`dist/index.html` がなければ「先に `npm run build:standalone` を実行する」と案内して止まる。
- **E2E の向き先**: `tests/e2e/helpers.cjs` の `APP_DIR` を `dist/` にして、`file://` で開く E2E は `dist/` を検査する。Web 版のテストのサーバーは `WEB_DIR`（`public/`）を配る。
- **リリース**: 同じビルド番号で、Web 版（`public/`）、スタンドアロン版（`dist/`）の順にビルドし、2 つの ZIP（`Lucivo-v<版>.zip`、`Lucivo-v<版>-web.zip`）を GitHub Release に付ける。リリースノートの冒頭には、利用者が選ぶのはスタンドアロン版の ZIP であることを書く。
- **公開用の Web 版**: `Lucivo-v<版>-web.zip` から作る。Web 版の中身だけを変えても、公開用の Web 版は GitHub Release の成果物と同じビルド番号を保つ。
- 採らなかった案:
  - `e2e.yml` の中だけで `dist/` を作る案: 手元で作り忘れると、古い `dist/` を検査してしまうため。
  - ZIP から Web 版だけのファイルを除く案: 公開用の Web 版は ZIP から作るため、ZIP から除くと公開用の Web 版からも消える。
  - `public/` をスタンドアロン版にして、Web 版の出力先を別に作る案: 公開用 URL・テスト用 URL・既存の CI が `public/` を前提にしており、変更が広がるため。
- 注意: `release.yml` と `deploy.yml` はリリースのときにしか動かず、手元で確かめられない。変更を小さく保ち、最初のリリースの後に、リリースノート・2 つの ZIP・公開用 URL の版とビルド番号を確かめる。

### 4.16 発表モードの登録と配布先ごとの出し分け（`ARC-MODE-001`〜`010`。`FR-054`, `FR-055`, `NFR-001`, `NFR-006`）

略号 `MODE` は、発表モードの登録の仕組みを指す。発表モードとは、発表のドロップダウンから選ぶ見せ方（ズーミング・マップ `FR-054`、プレイアブル・ダイアグラム `FR-055` など）である。ステージ発表（`FR-019`）は Visualモードの光の演出と同じ本体の部品（`stage.js`）であり、発表モードに含めない。

発表モードは、Web 版で先に提供し、利用者の反応を見て、廃止するか、スタンドアロン版にも展開するかを決める。追加・廃止・展開が定期的に起きるため、本体とモードを分け、モードの登録を 1 か所にまとめる。狙いは次の 3 つである。

1. 最も頻繁に起きる廃止の費用を最小にする。登録表の 1 行と、モードのファイルを消すだけで済ませる
2. スタンドアロン版への展開を、登録表の書き換えでほぼ済ませる
3. Web 版だけで提供している間は、文書とテストの費用を抑える。ただし、どのモードにも共通の品質（`ARC-MODE-007`）は外さない。段階ごとに求める文書とテストは `AGENTS.repo.md` 10 章による

利用者には段階を見せない。Web 版だけのモードも、正式な機能として提供する。

| ID             | 設計 |
| :------------- | :--- |
| `ARC-MODE-001` | **登録表**: 登録表は `src/ts/modes/modes.json` の 1 つだけとする。各行は `{ "id", "label", "stage", "gateSkip"? }` で、`stage` の値は `"web"`（Web 版だけで提供）か `"all"`（スタンドアロン版にも展開）である。メニューの項目・ビルドの対象・スタンドアロン版から除くファイル・共通の検査は、どれもこの表から作る。展開は `stage` の書き換え 1 か所で済み、廃止は行とモードのファイルを消すだけで済む |
| `ARC-MODE-002` | **配布先ごとの埋め込み**: `tools/build-app.cjs` が登録表を `require` で読み、配布先（4.15）で絞る（`standalone` では `stage: "all"` の行だけを残す）。絞った表は、esbuild の `define` で `__LUCIVO_PRESENT_MODES__` として `app.js` に埋め込む（版番号の `__LUCIVO_VERSION__` と同じやり方）。ビルドするモードと、スタンドアロン版にするときに除くファイル（`js/modes/<id>.js`・`css/modes/<id>.css`）も、同じ絞り方で決める。メニューに出すかどうかは埋め込まれた表だけで決め、実行時に `file://` かどうかを調べない |
| `ARC-MODE-003` | **`file://` で動く作り**: Web 版だけで提供している間も、`file://` で開いて動く作りにする。`fetch`、ES モジュールの `import()`、Worker、CDN は使わず、同梱のファイルを `<script>`・`<link>` で読む。こうしておけば、スタンドアロン版に展開するときに作り直さずに済む |
| `ARC-MODE-004` | **ファイルの置き方**: モードのソースは `src/ts/modes/<id>/` に置き、入口を `index.ts`、CSS を `style.css` とする（フォルダの中には、ほかのファイルも置ける）。出力先は `js/modes/<id>.js` と `css/modes/<id>.css` である。`src/ts/modes/` には、`modes.json` とモードのフォルダしか置かない。テストと文書も同じ `<id>` の名前で置く（下の表）。本体の CSS（`src/css/style.css`）は、モードの CSS を読み込まない |
| `ARC-MODE-005` | **メニュー**: 発表のドロップダウンの項目は、埋め込まれた表の順に、ステージ発表の後ろへ作る。HTML（`index.html`）に書く項目はステージ発表だけにする。項目に段階（Web 版だけかどうか）は表示しない |
| `ARC-MODE-006` | **本体とモードの境界**: 項目が選ばれたら、本体はそのモードの JS と CSS を（まだ読んでいなければ）読み込み、`LucivoModes.get(id).enter(host)` を呼ぶ。モードは、読み込まれたときに `window.LucivoModes.register(id, { enter, exit, info? })` で自分を登録する。`Esc` などの終わり方はモードが受け持ち、`exit()` の中で `host.restoreView()` を呼ぶ。モードが本体について知ってよいのは、host（下の表）と `LucivoModes` だけである。本体の中身（`window.state`、`window.updateAllSlabSplits`、`#btn-visual-mode` のクリックなど）には触らず、本体のモジュールを `import` もしない。DOM は、モードが自分で作った要素と、host から受け取った要素の中だけを触る。テストは `LucivoModes.get(id)` を通して `info()` などを呼ぶ。読み込みに失敗したときは、本体がトーストで知らせる |
| `ARC-MODE-007` | **共通の品質の関門**: `tests/e2e/present-modes.cjs` が登録表を読み、すべてのモードを Web 版で検査する。検査の項目は、始められること、コンソールにエラーが出ないこと、スマホの幅（390px）で横にはみ出さないこと、`Esc` で元の表示（高速 / Visual、Split / Canvas、スクロール位置）に戻ること、の 4 つである。`stage: "all"` のモードは、同じ検査を `file://`（`dist/`）でも行う。`stage: "web"` のモードについては、`dist/` のメニューに項目がなく、ファイルも入っていないことを確かめる。関門を通らないことが分かっていて直さないモードは、`gateSkip` に項目と理由を書く（例: `{ "narrow": "<理由>" }`）。例外も表の行の中に書くので、廃止のときに一緒に消える |
| `ARC-MODE-008` | **モードごとのテスト**: モードごとのテストは `tests/e2e/modes/<id>.cjs` に書き、`{ suites: [...] }` を書き出す（各要素は `tests/e2e.cjs` の `SUITES` と同じ形）。`tests/e2e.cjs` は、このフォルダのファイルを自動で集める |
| `ARC-MODE-009` | **消し忘れの検査**: `tools/check-modes.cjs` を `npm run lint` で実行する。登録表の各行について、ソース（`index.ts`・`style.css`）・テスト・文書（下の表）がそろっているかを調べる。逆に、登録表にない `<id>` のファイルが、`src/ts/modes/`・`public/js/modes/`・`public/css/modes/`・`tests/e2e/modes/`・各文書の `modes/` に残っていないかも調べる。ビルドは `public/` の古い出力を消さないため、出力の消し忘れもここで止める |
| `ARC-MODE-010` | **上位の文書にはモードを個別に書かない**: 要求仕様書（`doc/1.SRS.md`）、本書、テスト仕様の目次などは、モードごとの節を持たず、各 `modes/README.md`（目次）を指すだけにする。廃止のときに直す文書を、`modes/` の中のファイルと目次の 1 行に閉じるためである |

host（`enter(host)` で渡す）は、今あるモードが使う分だけにする。足りなくなったら、新しいモードを作るときに足す。

| host                      | 役割                                                                  | 使うモード                 |
| :------------------------ | :-------------------------------------------------------------------- | :------------------------- |
| `showVisualCanvas()`      | 今の表示（高速 / Visual、Split / Canvas、プレビューのスクロール位置、光の演出のオン・オフ）を覚え、Visualモードの Canvas 表示に切り替える。図の描画を待ってから `#visual-stage-container` を返す | ズーミング・マップ |
| `restoreView()`           | `showVisualCanvas()` で覚えた表示に戻す（光の演出のオン・オフを含む） | ズーミング・マップ         |
| `previewRoot()`           | 今の表示のプレビューの要素（Visualモードでは `#visual-stage-container`、高速モードでは `#standard-doc-container`） | プレイアブル・ダイアグラム |
| `isDocumentEmpty()`       | エディタが空かどうか                                                  | ズーミング・マップ         |
| `relayoutSlabs()`         | スラブの 2 段組みの判定をやり直す（4.9）                              | ズーミング・マップ         |
| `getMermaidSource(index)` | 図の番号から Mermaid のコードを返す                                   | プレイアブル・ダイアグラム |
| `setLights(on)`           | 光の演出を止める・再開する                                            | ズーミング・マップ         |
| `toast(message)`          | 案内を出す                                                            | 両方                       |

モードのファイルは、すべて `<id>` の名前にそろえる。目次の `README.md` は、各 `modes/` に置く。

| 種類             | 置き場所                                               |
| :--------------- | :----------------------------------------------------- |
| ソース           | `src/ts/modes/<id>/`（`index.ts`・`style.css`）        |
| ビルドの出力     | `public/js/modes/<id>.js`・`public/css/modes/<id>.css` |
| テスト           | `tests/e2e/modes/<id>.cjs`                             |
| デザイン仕様     | `doc/0.DTP/features/modes/<id>.md`                     |
| 要求仕様         | `doc/1.SRS/features/modes/<id>.md`                     |
| 詳細設計         | `doc/3.sw_design_notes/features/modes/<id>.md`         |
| 実装ドキュメント | `doc/3.implementation/js/modes/<id>.md`                |
| テスト仕様       | `doc/4.test_spec/modes/<id>.md`                        |

- **廃止しやすさの確かめ方**: 作業用のブランチで、ズーミング・マップとプレイアブル・ダイアグラムの行とファイルを消し、ビルド・lint・E2E の全件が通ることを確かめる。消したものは本線に入れない（型の検査は、`typescript` を依存に持たず実行していないため、条件に含めない）。
- 採らなかった案:
  - ステージ発表も登録表に入れる案: `stage.js` は Visualモードの光の演出にも使う本体の部品で、スタンドアロン版でも使う。表に入れると、消してよい部品のように見える。
  - 登録表を TypeScript で書く案: CommonJS のビルド（`build-app.cjs`）から読むのに変換が要る。JSON ならビルドからそのまま `require` できる。
  - `app.ts` が登録表を esbuild の JSON の取り込みで読む案: 表のすべての行が埋め込まれ、配布先ごとに絞れない。
  - メニューの項目を HTML に残す案: 登録する箇所が 2 つになり、消し残しの元になる。
  - Web 版だけのモードを、スタンドアロン版の ZIP にも入れて隠す案: スタンドアロン版の軽さ（`NFR-006`）を損なう。
  - スタンドアロン版からファイルだけを除き、埋め込む表は絞らない案: ZIP を社内のサーバーなどに置いて `http(s)://` で開くと項目が出てしまい、選ぶと読み込みに失敗する。
  - メニューに出すかどうかを、実行時に `file://` かどうかで決める案: 判定が登録表と実行時の 2 か所に分かれる。配布先で決めれば、Web 版の配布物を `file://` で開いた場合も Web 版と同じ項目が出るが、`ARC-MODE-003` により動く。
  - コード・文書・テストを、モードごとに 1 つのフォルダにまとめる案: 削除は最も楽だが、作業の流れに沿った文書の構成（`AGENTS.repo.md` 2 章）と、配布物の分け方が崩れる。
- 未決: 利用者の反応をどう判断するか。利用状況を集める仕組みは今はない。当面は、開発者本人の評価と GitHub の Issue で判断する。
